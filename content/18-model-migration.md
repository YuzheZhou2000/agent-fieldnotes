## 首轮成功之后，迁移风险才开始出现

一个代码 Agent 切换模型后，第一轮能正常回复，第二轮却在回传工具结果时失败。排查发现适配层只保存了 `role` 和 `content`，丢掉推理字段与工具调用记录。另一条轨迹能够完成，却因为改写历史工具定义反复失去缓存，单次请求看起来更快，整个任务的费用和重试次数反而增加。

这两个例子是用于说明故障模式的假设场景，不是本文发现的线上事故。它们指向同一个问题：长程 Agent 的迁移对象不止模型名，还包括保存了哪些状态、如何解释响应，以及哪些副作用允许再次执行。

2026 年 10 月 23 日，Kimi Code 更新日志宣布 K3.1 Pro 系列上线；本文在 **10 月 26 日**补充核查这一近期发布，不将检索日当首发日。官方技术博客称其基于 K3 继续后训练，并扩展联合 RL 的训练与环境基础设施；这些披露没有给出完整可复现训练配方。API 和产品可用也不等于权重已交付：博客仍将完整权重列为 **11 月 4 日前**的后续发布承诺。<sup><a href="#cite-1">[1]</a> <a href="#cite-2">[2]</a></sup>

本文采用公开接入文档讨论迁移，不复述模型榜单，不声称跑过 K3.1、下载过其权重或复现过厂商实验。以下标为“工程设计”的部分是本站推导，需在自己的系统中验证。

## 先区分发布、可用与退役三个时钟

截至核查日，官方模型列表写明：**2026 年 10 月 31 日起 K2 系列不向新注册用户提供，现有用户不受这一阶段限制；全部 K2 系列计划在 2026 年 12 月底退役。**后一个时间是计划，不是公告给出的精确某日。页面另列已经退役的旧 `kimi-k2-*` 等 ID，不能把这些旧条目和仍在售的 K2 系列混为一谈。<sup><a href="#cite-3">[3]</a></sup>

工程设计上，应为每个依赖记录三个独立字段：

| 字段 | 回答的问题 | 决定什么 |
|---|---|---|
| 发布证据 | 何时公布，哪些接口和工件真正可取得 | 能否开始验证，是否可本地部署 |
| 账户可用性 | 当前账户、地区、产品、端点是否有权使用 | 请求能否成功，灰度人群怎样划分 |
| 退役条件 | 哪些 ID、哪些账户、何种截止口径 | 迁移优先级与回滚窗口 |

不要用一次成功请求证明整个组织可用，也不要把尚未兑现的权重承诺纳入紧急回滚方案。新账户禁用与现有账户退役的时间不同，测试账户能否重建也可能影响灾备演练。本篇没有证据表明读者或本站维护者正在使用 K2；这里是依赖管理方法，不是个人迁移通知。

## 接入身份应是一组配置，而不是一个字符串

开放平台文档使用 `kimi-k3.1-pro` 和 `kimi-k3.1-pro-highspeed`；Kimi Code 文档使用 `k3.1-pro` 和 `k3.1-pro-highspeed`，还区分套餐可用性与上下文额度。错误说明明确要求区分 Coding Plan 与开放平台的密钥及端点。<sup><a href="#cite-4">[4]</a> <a href="#cite-5">[5]</a> <a href="#cite-6">[6]</a></sup>

因此，兼容某种请求外形只意味着能够表达请求，不足以证明产品权限、默认参数、账单和恢复历史均可互换。建议给每次任务绑定一个不含密钥的配置快照：

```text
provider_product  = 开放平台或 Coding Plan
endpoint_identity = 已审核端点标识
requested_model   = 精确模型 ID
response_model    = 服务端实际返回的模型标识
adapter_version   = 消息序列化与流式组装版本
reasoning_effort  = 显式选择的档位
history_format    = 持久化消息格式版本
toolset_revision  = 工具 schema 与执行器版本
policy_revision   = 当前授权策略版本
budget_revision   = 本次请求、总任务与重试上限
```

这是审计字段示例，不是可直接发送给 API 的请求体。密钥留在专门的凭据管理边界；记录凭据引用即可，不把秘密写进日志或模型上下文。

文档的默认值也应被当作接入风险：开放平台快速开始写 `reasoning_effort` 默认 `max`，Kimi Code 配置写默认 `high`；两者均列出 `low/high/max` 并要求思考开启。本文不尝试替不同入口统一默认值。显式传参、记录端点和实际响应，再验证成本及质量，通常比依赖默认值更容易追责。<sup><a href="#cite-4">[4]</a> <a href="#cite-5">[5]</a></sup>

## 完整消息是协议状态，展示文本只是其中一部分

K3.1 API 快速开始要求在后续轮次保留完整 assistant message；流式输出把 `reasoning_content` 和最终 `content` 分开，最终 JSON schema 应解析后者。工具返回通过 `tool_call_id` 对应调用。这里的核心合同是让下一轮收到服务所需的消息结构，而不是只保存用户看见的文字。<sup><a href="#cite-4">[4]</a></sup>

以下是工程设计中建议区分的三层数据：

1. **协议记录**：保存适配器能够无损重放的结构化消息，含必要扩展字段、调用标识和顺序；限制访问及保留期。
2. **用户视图**：显示最终回答、可公开的进度和工具结果摘要；可以做脱敏及排版，但不回写覆盖协议记录。
3. **业务账本**：独立保存实际动作、授权、操作键、外部回执与未知结果，模型消息不能替代这些事实。

“无损”要限定于已审查的协议边界。不要为方便把整个请求对象、凭据或不相关数据无限保留；也不要把供应商返回的推理内容当成可信授权或忠实的因果解释。必要字段如何加密、谁可读取、保留多久，是应用自身的数据治理责任。

### 两条容易被忽略的回归

**扩展字段丢失。**同一个消息经过数据库、队列、SDK 类型转换后，未知字段可能被丢弃。只测试内存对象的往返不够，应覆盖实际持久化链路。验收条件是下一轮所需字段与关系完整，不是序列化后还能打印一段文字。

**流式片段被误当完成动作。**函数参数可能跨多个片段到达，重复事件又可能来自重连。必须等该调用组装完整并通过 schema、权限和预算校验，才能进入执行器。连接中断时，未完成请求与已执行但未确认的动作应分别记录，不能一律重发。

## 动态工具定义进入历史之后，会多出一类状态

公开动态工具文档允许把完整 schema 放入没有 `content` 的 `system` 消息，在消息序列中的相应位置生效。声明按请求提供，服务端不会替客户端永久注册；保留原消息并在尾部追加新定义，可以保持已有前缀。该页当前明确列出 `kimi-k3.1-pro` 和 `kimi-k3`，不能据此推定 Highspeed 或其他模型具备完全相同支持。文档没有在此给出该机制首次发布日期，本文也不把它称作 K3.1 首创新特性。<sup><a href="#cite-7">[7]</a></sup>

原来的消息模型可能只有“用户提问、模型回答、工具结果”。加入动态声明后，历史中还存在“这一位置开始可见的能力描述”。这会影响压缩、重放、审计和缓存；不能按空 `content` 就删除一条消息。

下面是本站构造的序列示意，**不是供应商请求示例或已运行代码**：

```text
H0: 用户请求检查发布包
H1: 模型请求寻找适合的只读工具
H2: 应用返回工具目录的匹配结果
H3: 应用追加审核后的 read_manifest schema，版本 v3
H4: 模型请求 read_manifest，调用标识 c17
H5: 执行端校验授权并记录结果，再回传 c17 的结果
H6: 模型依据结果继续规划
```

这里至少有两种“工具存在”：目录中可发现，和当前请求中已声明。再加上执行端当前许可，实际是三个集合。一个工具被发现或被声明，都不意味着这次任务已经获得执行它的权限。目录结果也不能直接成为新的高权限系统指令；应用应从受信任的工具注册表选择并校验 schema，而不是把外部网页返回的任意描述注入控制面。

如果 `read_manifest` 升到 v4，直接改写 H3 会让旧轨迹失去原解释。工程上可记录版本化定义，并在新的决策边界启用新版本；若旧执行器无法继续服务，则明确中止或迁移任务，而不是对旧调用静默采用新含义。

## 保持前缀有利于缓存，但不能主导权限决策

动态工具文档按前缀匹配解释缓存：尾部追加不改写先前消息，删除或修改中间内容可能使之后的缓存失效。其目标是减少反复提交大工具集合带来的开销；实际命中仍需由服务返回的 usage 验证，不能仅凭请求结构宣称节省了多少成本。<sup><a href="#cite-7">[7]</a></sup>

下面的判断属于工程推导：

- **权限撤销优先。**即使删除工具定义会影响缓存，也不能为了命中率继续暴露或执行已撤销能力；执行端每次复核当前许可。
- **压缩视为迁移。**摘要可能保留任务目标，却丢掉动态工具定义、版本或调用关联。压缩后要重新构造合法协议状态，单独测试缓存和行为，不假设语义等价。
- **缓存键不能承载业务事实。**缓存成功不证明历史完整，更不证明前一次写操作已经生效；副作用仍查业务账本。
- **成本计算覆盖整条轨迹。**分别记录冷启动、热前缀、失效后重建、工具等待和返工。输入命中率与最终任务成本是不同指标。

一个实用取舍是将“正确性必需状态”和“性能优化状态”分开。前者缺失应阻止继续执行或进入明确修复流程；后者缺失可以使运行变贵，但不应悄悄改变授权与动作语义。具体容忍范围应由业务风险与预算决定。

## 给迁移设计一组可失败的验收条件

本文没有运行下列实验。表格是可以纳入团队测试计划的验收矩阵；先用本地模拟响应检查适配器，再在获得正常 API 使用授权与预算后验证真实端点。模拟通过只能说明应用处理了构造的案例，不能证明供应商行为或模型质量。

| 测试层 | 故障或对照 | 应保留的证据 |
|---|---|---|
| 身份与参数 | 错模型 ID、入口混用、不支持的 effort、静默回退 | 请求配置、返回模型、错误分类；不记录密钥 |
| 历史往返 | 空 `content`、必要扩展字段、两次序列化、恢复后再请求 | 字段、顺序与关联关系的差异 |
| 工具调用 | 单调用、多调用、错误结果、空结果、重复结果 | 每个调用与结果匹配；执行次数可核对 |
| 流式恢复 | 参数半包、断线、重放片段、完成标记缺失 | 已组装状态、未完成调用、是否曾派发 |
| 动态能力 | 声明缺失、schema 升级、压缩后恢复、许可撤销 | 请求中的可见集合、执行器版本和当前许可 |
| 成本与质量 | 新旧模型、冷/热历史、Pro/Highspeed、同一预算 | 最终任务判分、总耗时、使用量、工具错误与费用 |
| 退役与回滚 | 旧端点拒绝请求、旧模型已不可用、回滚时有在途操作 | 降级目的地、操作核对与人工交接结果 |

对于多调用响应，验收应允许多个独立调用，但不能因收到两次响应就执行同一个业务写入两次。模型调用标识用于协议关联，业务幂等键用于抵御重试；两者不应未经设计就视为同一个东西。不同提供方是否复用调用标识，也需要单独确认。

质量评估至少分开“产物是否正确”和“运行过程是否符合约束”。一次任务完成但越过权限、超出预算或留下未知副作用，不应被同一个成功布尔值掩盖。更详细的判分、预算和轨迹设计可结合[评测与交付专题](agent-evaluation.html)阅读。

## 灰度与回滚必须承认旧轨迹未必可移植

Kimi Code 明确建议从新会话开始，避免在旧系列会话中直接切换造成行为和缓存问题。这个产品建议不能自动推广为所有开放平台历史都不可迁移，但足以提醒团队：跨模型回放需独立验收，不能只比较相同 prompt 的首轮回复。<sup><a href="#cite-5">[5]</a></sup>

可采用以下工程发布顺序：

1. 固定当前基线和任务集，为新适配器做无副作用的协议测试。
2. 用新建会话做有限灰度，将旧长任务继续固定到原配置，避免任务中途静默切换。
3. 对确需迁移的在途任务，先停止新派发，核对已发生的副作用，再构造明确的新任务检查点。
4. 比较任务级成功率、延迟与成本分布，并人工审查失败类别，而不只看平均值。
5. 满足预定门槛后扩大流量；触发异常时回到仍可用且已验证的配置，或进入人工接管。

回滚代码不等于回滚外部世界。新模型已经创建的文件、提交、工单或付款请求，不会因路由切回自动消失。模型退役之后，原模型也可能不再是可用回滚目标。应提前决定哪些任务可以安全重开，哪些必须人工核对；相关账本方法见[服务化与故障处置](agent-operations.html)。

## 这次发布值得留下的工程结论

K3.1 的近期接入与退役信息提供了一个具体迁移案例。可迁移的知识是：把端点身份、协议记录、能力声明、执行授权和业务事实分层；给每层定义版本和失败条件，再通过任务级证据决定是否切换。

官方技术博客中的内部评测与速度声明，不足以替代自己的任务、工具、Harness 和预算对照；本文不采用其排名或幻觉率数字。权重发布兑现、真实端点验收和独立模型评测也仍是不同事件，不能用一个“已验证”概括。

本篇接入[模型适配学习站](../learn.html#learning)与[长任务状态站](../learn.html#durability)，覆盖的是推理接入与迁移，**并未补齐 SFT、偏好优化或 RL 训练教程**。进一步可读[运行时恢复](openai.html)、[长任务历史](claude.html)与[权限边界](agent-containment.html)，把模型升级放回完整 Agent 系统中理解。
