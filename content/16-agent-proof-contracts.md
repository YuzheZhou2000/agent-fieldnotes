## 从“测试通过”到一个有边界的命题

代码 Agent 说“修好了”，测试系统说“这些样例通过了”，形式化检查器说“这个命题由这些前提推出”。三者提供不同证据。团队需要先决定验收哪一种性质，再选择相应工具，而不是把越来越长的成功日志当作越来越强的保证。

Anthropic 与 Theorem 在 10 月 22 日披露：将 OSS-Fuzz 入口对应的程序编译成 RISC-V 二进制，由 Claude 生成证明、Rocq 检查，研究活动覆盖 123 个库中的 239 个入口。这里的对象是特定构建、入口和模型化条件，不是这些库在所有部署方式下都没有漏洞。公告给出 64 MB 的输入边界，并限定单线程、静态链接和固定内存预算。<sup><a href="#cite-1">[1]</a></sup>

值得借鉴的系统设计是把“生成候选”与“接受候选”分离。模型可以探索引理、修改证明、读取报错；决定命题是否成立的验收接口仍由独立检查器承担。检查器能缩小需要人工相信的范围，却不能代替人判断命题是否对应业务需要。

## 公开结果要单独数，命题不能计作已证明

核查时公开仓库快照为 8f5f46768858af236a4270f9628e6beed9aa0e72，提交时间 2026-10-22 20:28:58 UTC。README 列出已公开证明涉及 25 个库、60 个入口，采用 Rocq 9.2.0；其大规模命题目录不能直接作为成功数量。研究整体与公开子集应分别陈述。<sup><a href="#cite-2">[2]</a></sup>

公开证明使用 LPS 对 Linux 进程的形式模型，比较普通构建与 sanitizer 构建在预算内输入上的可观察行为，并排除命题所定义的错误。这不等于业务输出正确，也不排除 sanitizer 未覆盖的问题，例如内存泄漏。LPS 本身是有缺漏和假设的模型，不是完整 Linux；可信基础还包含 Rocq 内核、允许的公理、二进制装载工具和检查包装器。<sup><a href="#cite-2">[2]</a></sup>

尤其要检查保证的类型。该公开版本的 agreement 证明不排除永不结束的运行，README 明确说明未发布证明 halts 命题的结果。因而“没有证明范围内的错误”不能改写成“一定正常退出”；研究公告关于正常退出的整体概述，也应与公开版本实际列出的命题分开核对。同样，源代码相同也不能把特定静态 RISC-V 构建的结论直接转移到动态链接的 x86 或 ARM 程序。<sup><a href="#cite-2">[2]</a></sup>

## 一个可复用的验收合同

以下是工程设计建议，不是作者实现的复述，也不是本次已执行的实验。

让 Agent 提交一个证据包，至少明确六件事：

1. 对象：仓库提交、构建参数、工具链和二进制哈希。
2. 性质：要排除什么错误；是否要求终止、性能上限或输出正确。
3. 范围：入口、输入集合、资源预算、平台与外部系统假设。
4. 可信基础：检查器、语义模型、允许的公理及导入的依赖。
5. 重放方式：固定版本、命令、资源限制和机器可读结果。
6. 未覆盖内容：不能从当前结果推出哪些上线承诺。

验收端应接收证据包，而不是接收一句“检查已通过”。必须由验收端重新确认哈希、命题及检查结果属于同一个候选版本。文件时间戳接近、分支名一致、Agent 的日志里出现绿色文字，都不足以建立这个绑定。

若 Agent 在证明失败后修改了程序，旧候选必须失效。重新构建、重新生成目标、重新检查，还要独立审查业务语义是否被削弱。禁止把删除功能、吞掉错误或缩小输入域产生的容易证明版本悄悄当作原目标的完成。

## 失败时，先定位失效的合同

以下是验收端的工程推导，不是已经实现的本站工具：

| 观察 | 不能直接推断 | 下一步 |
|---|---|---|
| 证明文件存在 | 目标命题已证明 | 检查对应版本、命题类型和允许假设 |
| 检查超时或内存不足 | 命题为假 | 区分资源失败与反例，记录预算后再决定是否扩容 |
| 检查通过但二进制哈希变化 | 新程序继承旧结论 | 使证据失效，重建目标并重新检查 |
| 删除断言或缩小输入域后通过 | 原任务已完成 | 审查规格差异，重新取得验收目标的一致意见 |
| agreement 通过 | 运行一定终止 | 为终止性质另设命题与检查结果 |

形式检查适合性质能被清楚表述、对象可冻结、投入可以摊销的边界。开放式需求、外部服务和不断变化的部署仍需测试、监控与业务验收；证明不是替代这些层次的总开关。

## 计算费用与检查费用都应入账

附录说明，生成的证明包含大量工具产生的内容；单个证明的检查可能消耗半小时到数小时 CPU 时间。用于模型比较的小任务集也做了专门缩减，包括更小输入与简化运行时，不能当成完整生产库的普遍成本基线。<sup><a href="#cite-3">[3]</a></sup>

因此比较两种 Agent 方案时，应统计证明搜索、失败尝试、候选补丁审查和验收重放的总成本。只报告最终证明的 token，或者只比较模型生成速度，会漏掉实际交付链中的主要支出。

一个合理的入门实验是先选一个已有测试入口，固定输入边界与构建，尝试重放一份已有公开证明，再研究如何扩展目标。优先测“证据是否可重复检查”，不要一开始就以整个仓库无漏洞为目标。这里未下载检查器、安装工具链或复现任何公开证明。

本专题承接[长任务评测](agent-evaluation.html)中产物与 grader 的区分，也补充[Agent Teams](agent-teams.html)里的证据交接：成员传来的证明文件可以共享，但不能自动获得验收权威。把“可检查的产物”作为协作接口，是比角色数量更重要的设计选择。
