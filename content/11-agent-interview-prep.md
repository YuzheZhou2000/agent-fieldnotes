### 1 2 三种岗位的知识边界

**Agent 应用与 Coding Agent**：重点是任务规划、工具、上下文、代码库理解和评测。需要理解模型训练与推理基本流程，但不要因为岗位含“大模型”就把全部时间投入训练公式。

**Agent 后端与 Runtime**：重点是状态机、恢复、并发、队列、工具执行、沙箱、权限、成本、观测和发布。能解释某次调用为什么超时、某个任务为什么重复执行，比列举框架更有信息量。

**Agent 全栈与企业交付**：除上述内容，还要准备流式交互、任务时间线、人工接管、桌面应用边界、组织身份、多环境部署和升级兼容。投腾讯 J3 时补充 React／TypeScript／Electron 及相关工程实践；投 Go 后端 J2 时把时间优先给 Go 与系统设计。

算法训练、RL、推理 Infra 是相邻赛道。只有 JD 明确强调训练、算子、GPU 或推理引擎时，才把这些提高到主线。

### 1 3 如何比较 Qoder 与 WorkBuddy

Qoder 官方 Repo Wiki 文档描述了代码库知识生成、增量刷新和任务引用；它也提醒关键结论应回到当前代码、配置、测试和运行结果验证。WorkBuddy／CodeBuddy 企业智能体文档定义了 Agent、Runtime、Session、沙箱、凭据和渠道接入等对象。这两组材料适合分别引出代码知识工程与企业运行平台的问题。[T1 Qoder Repo Wiki](#cite-4)、[T2 腾讯企业智能体](#cite-5)。

**准备时的推导**：Qoder 路线多练“找到改动位置并正确交付代码”；WorkBuddy 路线多练“跨工具完成工作并保留可控的权限和状态”。这是依据产品与岗位要求的复习侧重，不是对内部架构或面试权重的断言。

### 2 1 值得直接练习的三条追问链

**效果数字链**：你说效果很好 → 衡量的是什么 → 数据从哪里来 → 样本如何抽 → 标注是否一致 → 是否独立测试集 → 是否区分类别与难度 → 线上是否验证 → 失败集中在哪。先准备清楚口径，再准备漂亮数字。

**上下文链**：消息如何入场 → 哪些进入模型 → 为什么检索这些内容 → 何时压缩 → 压缩掉什么 → 摘要过时怎么办 → 前缀缓存有何变化 → 如何证明成本下降而任务质量没退化。

**可靠性链**：一次调用失败 → 能否重试 → 外部动作是否已发生 → 如何识别重复 → 怎样恢复状态 → 发布时如何处理旧任务 → 用户取消后如何阻止继续执行 → 谁来收敛未知结果。

### 2 2 使用面经时的筛选规则

优先读带具体项目、追问和失败边界的原帖。只有时间线的帖子可以了解流程，不能提取技术题；付费汇总的公开部分不能代表全文。标题“面试某 AI 产品，当场下 Offer”的产品体验稿，不能当真人求职面经。带工具推广的综合帖仅作低权重线索，不用于统计所谓全行业高频率。

本题库不声称提供频率统计。这里的“优先”表示对目标岗位的准备价值，而非某题有多少概率出现。

## 4 Agent Loop 工具与编排题库

本节及后续题库中的题目均为复习与模拟题；与公开面经主题对应的题号用于定位练习，不意味着原帖逐字提问。

### Q01 Agent 与 Workflow 怎么选择

**答题要点**：工作流由代码决定流程，Agent 在约束内根据模型判断选择下一步。输入类型、步骤与验收清楚的任务优先固定流程；路径难以提前枚举、需要观察环境后调整的任务适合 Agent。实际系统常采用“外层工作流保证状态与权限，内层 Agent 解决开放子问题”。

**追问**：发票处理为什么不一定需要 Agent？先判断 OCR、字段抽取、校验和审批能否用固定步骤完成；只有例外处理或跨系统调查需要额外自主决策时再引入。

参考：[T3 Anthropic 的架构分类](#cite-12)。

### Q02 如何实现 Agent Loop 并判断停止

将 Loop 看成可恢复状态机：构建上下文 → 请求模型 → 解析响应 → 校验并执行工具 → 持久化观察 → 下一轮。至少区分完成、等待人工、失败、取消、预算耗尽与结果未知。

**没有 tool call 只是模型本轮没有请求工具**。还要检查拒绝、输出截断、格式异常、完成证据与验收条件。达到步数上限应返回明确的未完成状态，而不是伪造完成。工具的失败也不一定终止整个任务，应按可重试、可换方案、需人工处理分类。

```text
读取任务状态与固定版本
循环：
  检查取消、deadline、成本和步数预算
  读取 checkpoint，按状态版本构建上下文
  调用模型并持久化响应
  若响应需工具：
    完整解析参数；检查 schema、权限与动作边界
    为每个动作创建 operation_id 与执行记录
    执行或恢复动作；记录成功、失败或 UNKNOWN
    有未决外部写入时，先收敛结果再继续
  否则：
    校验任务产物和验收条件
    完成则结束；需人工则持久化等待；其他返回明确状态
```

这是控制流程伪代码，实际实现还需处理并发控制和持久化故障。

### Q03 Harness 的职责是什么

可以把 Harness 定义为模型周围的运行控制系统：管理上下文、工具目录、权限、资源、状态、重试、恢复、观测和验收。模型提出动作，执行系统决定动作是否允许、如何执行以及结果如何落盘。

**关键取舍**：权限、预算、幂等和状态合法性应由确定性代码校验。不要把“是否允许访问另一租户文件”“是否可以重复发消息”交给 Prompt 自由判断。复杂路径选择可以给模型，但必须保留工程边界。

**追问**：同模型更换 Harness 为何效果不同？上下文质量、工具反馈、搜索定位、错误恢复和验证机制都可能改变结果，需固定模型做对照实验。

### Q04 可靠的 Tool Calling 接口怎么设计

接口要有明确名称、语义、输入和输出结构。尽量用业务级操作减少模型拼装细碎步骤；限制路径、分页、返回量和超时；错误返回包含稳定错误码、是否可重试以及必要的补救信息。读写分开，副作用显式标注。

参数必须收集完整并通过校验后再执行，不能拿流式输出的一半 JSON 启动动作。正确的 JSON 只解决格式，不保证账号、金额、路径或业务前置状态合法。输出也要验证结构和证据来源。[T4 MCP Tools 规范](#cite-13)。

### Q05 工具调用超时能不能重试

先问工具是否有副作用。纯读取通常可以在 deadline 内重试；写入超时意味着结果未知，不能直接假设失败。为动作生成稳定幂等键，记录请求与执行意图，再通过外部查询、回调或对账确认结果。只有目标系统能按同一幂等键去重，重放才安全。

**反例**：邮件已发送、客户端没收到响应，再重试可能发两封。仅在本地记录“已经调用”也不够，因为记录与外部执行之间存在崩溃窗口。没有幂等或查询能力时，应停止自动重放、标记 UNKNOWN 并提供人工处理路径。

### Q06 多个工具调用何时可以并行

并行适合互不依赖、通常只读的操作。先构建依赖关系，限制全局和任务内并发，聚合结果时保留每个调用的身份、错误和顺序要求。

两个修改同一文件或同一业务对象的操作即使模型一起返回，也不一定能并行。使用版本校验、串行化或事务解决冲突。部分失败时区分“整体失败”和“可用结果不足”，避免无条件重复已经成功的写操作。

### Q07 Planning ReAct 与 Reflection 如何落地

规划提供目标和依赖，ReAct 让行动根据工具观察迭代，Reflection 是基于反馈修正方案。工程上保留结构化计划、当前步骤、完成证据和失败原因；只有依赖变化或连续无进展时才重新规划。

反思必须有外部反馈：测试错误、编译输出、检索证据或用户约束。让同一模型无依据重复点评，容易增加成本而没有增益。比较引入反思前后的成功率、步数和延迟，给迭代设预算。无需要求模型暴露完整私有推理过程，记录决策摘要与可验证动作即可。

### Q08 什么时候使用多 Agent

任务可独立拆解、不同子任务需要不同工具或上下文时，可以分工；共享状态很多、步骤严格依赖时，单 Agent 或明确工作流可能更容易控制。

多 Agent 的设计应包括输入输出契约、工作空间隔离、总预算、取消传播和汇总验收。Coding 场景可分别生成补丁后统一集成，避免多个执行者直接改共享目录。不能用“角色更多”证明效果，需要同模型、同任务、同总预算比较。

### Q09 Skill MCP API 和框架分别解决什么

API 暴露业务能力；MCP 规范能力发现和调用等交互；Skill 通常提供任务使用说明，并可带脚本与资源；框架提供状态、编排和模型适配等组件。Skill 与 MCP 可以组合，不能笼统说一个取代另一个。

Skill 还需要版本、来源、依赖、权限和兼容测试。文档里写“需要确认”并不能替代执行层权限校验。WorkBuddy 官方连接器文档介绍了 MCP 加 Skill 和 CLI 加 Skill 两种接入路径。[T5 WorkBuddy 连接器](#cite-14)。

### Q10 MCP 应该讲到什么深度

先讲 Host／Client／Server 角色，以及 tools、resources、prompts 的用途；解释本地 stdio 与远程 Streamable HTTP 的区别，远程调用的认证、授权、超时与错误边界。然后结合自己写过的服务讲 schema、分页和副作用控制。

**版本提醒**：本次检索的官方 2026-07-28 文档使用无状态请求与 server/discover，和不少旧教程的初始化流程不同。面试时先说明自己实现的协议版本，不把某一版握手步骤说成永远不变的规则。[T6 MCP 当前架构](#cite-15)。

**这一组的练习验收**：能从“模型要执行写入”一直讲到“任务恢复后怎样确认只发生一次业务效果”，不能止步于调用函数。

## 5 上下文 记忆与代码检索题库

### Q11 如何组织上下文

按决策需要组织，而非把所有历史拼接。分层放入稳定规则、任务目标与约束、当前计划、相关知识、最近动作和必要观察。每条重要信息尽量带来源、时间、权限范围、版本及适用条件。

预算至少给输出和下一次工具结果留空间。遇到冲突优先执行可信约束，代码事实优先回查当前工作树。通过消融实验验证某种上下文是否有用：固定任务与模型，比较是否检索、不同排序和不同预算，而不只看 token 减少。

### Q12 长任务怎样压缩上下文

先截断冗余工具输出、把大对象保存为可回查的引用，再对较早历史生成结构化摘要。保留目标、用户限制、关键决定、未完成事项、当前文件版本、失败方案和未决副作用；完成后的流水信息可以压缩。

压缩阈值需要为调用结果和输出预留预算，不能只写一个任意的“80%”。原始记录保留在外部存储，摘要可回溯。测试摘要后能否继续完成任务、是否重复已完成操作、是否丢约束。Anthropic 讨论了压缩与外部结构化笔记两种方法，但具体阈值要由自己的任务测试决定。[T7 上下文工程](#cite-16)。

### Q13 同步摘要和异步摘要怎么选择

同步摘要在下一次模型调用前完成，状态容易一致，但阻塞任务。异步摘要降低等待时间，却有摘要过时和覆盖新消息的风险。

给摘要绑定基础状态版本及“覆盖到的事件序号”；只有版本条件符合时才应用，随后拼接未覆盖的消息尾部。过时摘要丢弃或重算。后台任务也必须有幂等、限额与取消机制。不要把仍在执行的 tool call 从历史中压缩掉而丢失配对关系。

### Q14 记忆如何写入 更新和遗忘

区分会话执行状态、用户偏好、项目事实和跨任务经验。写入候选来自显式指令或有证据的观察；经过去重、冲突判断和作用域检查后落库。记录来源、置信度、版本、TTL、纠正与删除信息。

“用户以前要求测试使用 SQLite”不等于当前生产架构也应使用 SQLite。用户纠正应更新或失效旧记忆，而非追加两个矛盾条目。项目事实在代码变化时重新验证。召回阶段按相关性、时效与权限过滤，不能依赖模型自行分辨不同租户的记忆。

### Q15 为什么不能把所有历史放进向量库

历史中混有噪声、临时观察、错误猜测和敏感信息。直接入库会把旧错误持续召回，也难以区分事实与偏好。先定义记忆类型和生命周期，再选择检索方式。

结构化配置适合键值或关系存储；语义经验适合向量检索；执行状态需要可靠持久化，不能只靠相似度找回。评估记忆要看任务收益和错误记忆造成的损失，不能把召回条数越多当作越好。

### Q16 RAG 各阶段如何定位错误

把链路拆成解析、切分、索引、召回、重排和生成。先看正确证据是否入库，再看是否被召回、排名是否足够靠前、是否进入上下文，最后检查模型是否正确引用。分开测检索与最终回答。

固定长度切分容易割裂标题、表格与代码。可按章节、函数和语义边界切分，保留父文档、路径、行号与版本；适当重叠是取舍，不是固定答案。top-k 和 chunk size 应在任务集上测延迟、召回与回答质量后决定。

### Q17 百万行仓库怎么找到修改点

先从任务里的错误、接口、文件名和业务名做文本检索，再利用符号、调用关系、依赖图或语义检索扩展。读取入口、关键实现、调用者和测试，形成可验证的影响面。检索命中不等于定位正确，需要用运行结果或测试证明。

索引至少区分仓库、分支／commit、文件内容哈希和访问范围；叠加未提交改动与删除文件。新代码未入索引时回退实时读取。代码图能补结构关系，动态调用和配置连接仍需要其他证据。

### Q18 Repo Wiki 与代码索引如何增量更新

建立源文件与派生产物的依赖关系，变更后优先更新受影响实体、关联知识卡片和必要摘要。不能因改一个注释就无条件重建全部仓库，也不能只更新一个 chunk 而忽略调用者。

发布新索引快照，读者使用一致版本；失败保留旧版与过期标识。模型生成的知识要带证据引用并可纠正。Qoder 文档支持增量刷新，但文档不能保证运行行为，因此关键知识仍需对照当前代码验证。[T1 Repo Wiki](#cite-4)。

### Q19 KV Cache Prompt Cache 与结果缓存有什么区别

KV Cache 是推理过程中已计算的注意力状态；跨请求前缀缓存复用共同前缀的相关计算，主要节省 prefill；结果缓存复用完整业务响应。相同问题、相同前缀和相同业务状态是不同的命中条件。

稳定规则靠前、动态内容靠后、序列化和工具顺序稳定，有助于前缀复用。频繁重写早期摘要会改变后续前缀。缓存键与路由需考虑模型、版本、上下文和隔离策略；语义结果缓存还要判断数据时效与权限。vLLM 官方指出 APC 不减少生成新 token 的 decode 时间。[T8 vLLM APC](#cite-17)。

### Q20 缓存命中率变高为什么任务仍更慢

可能缓存的只是较短前缀，命中的 token 比例没有明显增长；也可能 decode、工具、排队、检索或摘要耗时变大。实例路由和缓存驻留不同也会影响复用。

至少分别观察请求命中率、可复用 token 比例、prefill 耗时、首 token、任务总耗时和任务成本。提供商返回的 cached token 口径不等于你能直接看到 GPU KV 块命中率。用同任务分布做对照，避免把短请求数量变化误读为优化。

## 6 评测 质量与效果题库

### Q21 如何构建 Agent 评测集

先定义用户任务和成功状态，再构造输入、初始环境、允许动作和验收器。覆盖正常路径、缺信息、工具故障、长任务、越权和取消等类别。代码任务固定起始 commit、依赖和隐藏测试；办公任务校验内容及最终文档或业务状态。

开发集用于迭代，独立保留测试集；近重复任务、同一文档或同仓库家族要避免无意泄漏。建立金标和人工争议裁决，按来源、难度、长度与能力切片。合成任务可以补覆盖，但需检查可解性和验收一致性。

### Q22 评测 Agent 应该看哪些指标

至少三层：最终任务是否成功，工具和执行过程是否可靠，成本和耗时是否可接受。统计自动完成率、需要接管率、工具失败率、越权尝试、取消收敛、P50／P95 总耗时、单位成功任务成本。

同一任务重复运行以观察稳定性。pass@k 表示多次尝试至少一次成功，pass^k 强调多次全部成功；前者不能直接当成用户一次使用的成功率。Anthropic 的评测指南也强调最终状态与执行轨迹的不同用途。[T9 Agent 评测](#cite-18)。

### Q23 如何解释意图识别 95% 准确率

先回答分母是什么、标签怎么定义、测试集来自哪里、是否包含真实长尾和未知意图、是否多标签。类别不均衡时总体 accuracy 可能掩盖重要类别的错误，应看每类 precision／recall、macro-F1、多意图匹配与拒识效果。

线上观察不是天然金标：点击或继续对话只能是代理信号。报出样本量、采样周期和不确定性，检查误差分布和业务损失。不要以模型自己的“置信度 0.95”替代经过标注的准确率。

**可直接套用的句式**：“这里的 X% 指在 N 条独立标注样本上，按某规则统计的某指标；我们还看了某类的召回和线上某项指标。”没有这些信息时坦诚说尚未建立完整口径。

### Q24 LLM as Judge 如何避免误判

给 Judge 清晰评分项、证据和反例；用人工样本校准，一致性不足的类别保留人工。控制答案位置、篇幅偏好、评审模型变化和评分 Prompt 版本。被评分内容中的指令不能改变评审规则。

可以执行的测试、文件内容或数据库最终状态，优先确定性验证。模型评审适合语义质量或难完全编码的维度。不要由生成答案的同一条推理轨迹直接给自己颁发成功结论。

### Q25 如何证明上下文方案有效

固定模型、工具、任务环境与预算，只改变上下文策略。比较任务成功率、检索证据覆盖、错误类型、token、时延和成功任务成本；对长任务、跨文件和难题分别分析。

线上可按用户或会话等合理实验单元分流，保持分流稳定，避免共享记忆把实验组结果污染控制组。提前约定成功指标和稳定性护栏。整体提升可能来自任务变简单，不能只比较两个时间段的平均值。

### Q26 SWE bench 成绩能说明什么

它适合检验在给定仓库和任务环境下修复软件问题的能力，是 Coding Agent 的一个能力切面。比较成绩时应确认数据集版本、模型、Harness、工具、尝试次数、预算和是否采用额外选择机制。

它不能直接代表企业内部仓库、前端视觉验收、业务需求澄清、权限和真实上线效果。项目准备中可以使用小型仓库任务集，说明它与公共 benchmark 的关系和局限。[T10 SWE-bench 官方页面](#cite-19)。

### Q27 如何建立失败归因与回归体系

以轨迹和最终状态区分：需求理解、检索缺失、规划、工具选择、参数、执行环境、权限、模型输出、验证器或状态恢复问题。一个 case 可能有主因与伴随因素，先定位最早导致失败的可修复节点。

把高影响失败转成固定环境的回归用例，发布时保留模型／Prompt／索引／工具版本。改工具后不要只测正常调用，应测超时、重复、输出漂移与权限拒绝。目标是用分类指导修复，不是给所有失败贴“模型幻觉”。

## 7 Runtime 后端与线上治理题库

### Q28 长任务如何持久化和恢复

持久化任务状态、事件、计划、上下文引用、预算、配置版本和动作记录；在有意义的步骤边界写 checkpoint。恢复时按事件序号重放，并先收敛未决外部动作。保存聊天文本不足以恢复执行现场。

LangGraph 的 checkpointer 维护线程内状态，store 维护跨线程应用数据；内存 saver 不能跨进程重启保存。即使用了持久化框架，外部动作仍需要幂等与结果确认，checkpoint 本身不提供外部系统 exactly-once。[T11 LangGraph Persistence](#cite-20)。

### Q29 同一会话多条请求如何处理

先确定产品语义：串行对话、打断当前任务，还是分叉成独立 run。区分 conversation、run、step 和 operation 的身份。一个会话需要更新共享上下文时，采用单写者或带版本的 CAS，工具只在依赖允许时并发。

如果用户新消息改变当前目标，应持久化新要求，在安全边界停止或调整旧任务；不能让两条 Loop 把彼此消息交错写入。隔离执行空间和返回事件，前端不要把两个 run 的输出混在一起。

### Q30 用户取消后怎么保证任务真的停止

取消是持久化的业务状态，而不仅是关闭前端连接。标记 cancel_requested，通知执行者，在模型和工具执行前检查；将取消传给可取消的请求和子进程，并对进程组执行终止与超时兜底。

已发生的外部写入不能因取消自动撤销。对不可取消动作先确认结果，再记录完成或未知；新动作不得继续启动。面试要区分用户连接断开、run 取消、某个工具停止和业务效果补偿。

### Q31 沙箱生命周期怎么设计

创建 → 初始化 → 就绪 → 执行 → 空闲／暂停 → 回收，另设失败和恢复路径。每个阶段有超时、租约、心跳、状态版本和可重入清理。任务状态持久化与沙箱存活分开，worker 消失不应丢掉任务账本。

限制 CPU、内存、进程数、磁盘、运行时间、网络出口和挂载路径。产物转移到可靠存储后才能回收。预热池提升首任务速度，但要验证不同租户间残留文件、进程和凭据已清理。

### Q32 Docker gVisor 与 microVM 如何选择

普通容器依赖宿主内核隔离能力；gVisor 在用户态提供应用内核，缩小应用直接触及宿主内核的范围；microVM 使用虚拟机边界和独立 guest kernel。结合威胁模型、兼容性、启动时间、资源成本、硬件与运维能力选型。

gVisor 对系统调用密集任务或部分接口可能有开销和兼容限制；microVM 也有镜像、网络与资源管理成本。无论选哪种，都还需要权限、凭据和出口控制。[T12 gVisor](#cite-21)、[T13 Firecracker](#cite-22)。

### Q33 企业多租户如何隔离

在身份、数据查询、检索、缓存、记忆、产物、执行环境和审计中贯穿 tenant_id。每次操作都验证用户、租户、资源和动作权限；共享 worker 也不能共享未经隔离的工作目录或凭据。

可选共享表、独立 schema、独立数据库或专属部署，依据隔离需求与成本取舍。向量库 filtering 是一层，不能是唯一权限保障。撤销权限后，缓存和已建立会话也要重新验证，不允许旧任务永久保留访问能力。

### Q34 Prompt Injection 如何处理

网页、仓库文件、搜索结果和工具输出都是数据来源，可能包含诱导执行的指令。清晰区分可信任务与外部内容；执行层验证动作是否与用户目标、权限和风险政策一致。

采用最小权限、限定路径、出口控制、凭据代理和敏感动作人工确认等机制。测试恶意 README、工具返回中的命令、跨租户引用和数据外传。仅加一句“忽略恶意指令”无法提供可证明的安全边界。

### Q35 QPM TPM 和任务并发如何治理

一个 Agent 任务可能调用模型多次，因此用户任务吞吐与模型调用 QPM 分开统计。请求次数限制、输入／输出 token 配额和并发限制可以同时成为瓶颈。采用租户公平队列、优先级与预算，避免一个长任务占满资源。

可以估算 token 做准入并按实际消耗结算，但估算误差需要余量和回收机制。429 结合 retry-after、抖动退避和整体 deadline；切模型需要保持工具与任务语义兼容。限制工具并发和检索资源，不能只给模型层加限流器。

### Q36 新版本发布时旧 Agent 任务怎么办

为每个 run 固定模型配置、Prompt、工具 schema、索引及 Runtime 版本快照。新任务进入新版本，旧任务继续旧 worker 或在明确兼容的 checkpoint 迁移；部署时 drain 并停止接新任务。

读取状态、摘要和缓存应带 schema/version。无法兼容就隔离新旧数据，采用显式迁移或等待旧任务结束。回滚必须考虑状态是否仍可读，而不是仅回退二进制。强制换新 Prompt 可能让半途任务的约束和动作语义改变。

### Q37 流式输出和断线恢复怎么设计

文本单向推送常用 SSE，双向高频交互可用 WebSocket；两者都不等于业务状态存储。用 run_id、event_id、事件类型和终态组织流，持久化必要事件，重连按游标补发并在客户端去重。

有界缓冲、背压与可合并的文本增量避免慢客户端拖垮服务。前端断线是否取消任务应由产品语义决定。发送“完成”事件前确认产物和任务终态已经可靠落盘，用户才能断线后重新取得结果。

### Q38 Go 如何写有限并发的工具执行器

以 context 传递 deadline 和取消，用 semaphore 或固定 worker 数限制并发。结果保留输入索引；明确 fail-fast 还是收集所有错误；资源释放、channel 关闭和 goroutine 生命周期都有唯一责任方。

不能启动无上限 goroutine 后靠下游限流兜底，也不能让子任务忽略 context。任务超时后观察 goroutine、连接池和进程是否收敛。讲清锁保护对象、共享状态和工具调用的副作用边界，才算完成这个设计。

### Q39 MQ 事务和幂等如何配合

数据库事务保护本地状态变更；outbox 将状态和待发布事件放进同一事务，发布者可重复投递，消费者用稳定事件身份去重。任务调度常按至少一次设计，租约和 fencing token 防止失效执行者继续提交。

Redis 锁不替代数据库唯一约束，队列标记成功也不等于外部操作已完成。对“状态落库成功但消息丢失”“消息收到但 worker 崩溃”“外部动作成功但结果没落库”分别画时间线，方案才可审查。

### Q40 怎么排查 Agent 突然变慢或质量下降

沿任务拆解：排队、上下文构建、检索、摘要、模型 prefill／decode、工具、沙箱启动和产物验证。按地区、租户、模型、Prompt、工具、索引与 Runtime 版本切片，与最近变更对齐。

保留 run → step → model call／tool call 的 trace，原文按权限采样与脱敏存储，指标聚合展示。先提出可证伪假设，例如“索引新版本漏召回”或“共享额度打满”，再用对照验证；不要看 endpoint 健康就认定模型服务与任务都正常。

## 8 工程基础 模型基础与产品题库

### Q41 gRPC HTTP 与 HTTPS 怎么回答

HTTP 是应用协议，HTTPS 通过 TLS 保护 HTTP 通信，gRPC 是 RPC 框架，常用 protobuf 与 HTTP/2；它们不是三个平行互斥的选项。gRPC 适合内部强类型接口和流式调用，JSON HTTP 对接浏览器和第三方更直接。

比较序列化、兼容性、流式、调试、deadline、取消和服务治理，结合真实调用链说明选择。TLS 的关键是验证身份与协商会话密钥，不是“每一条业务数据都用非对称加密”。背握手步骤后要能解释证书校验失败和超时怎么定位。

### Q42 K8s 扩缩容对 Agent 服务有什么特殊问题

仅按 CPU 扩容可能看不到模型等待、队列积压或沙箱冷启动。根据服务职责选队列等待、活跃 run、并发容量、沙箱池和启动耗时等指标。控制最大副本和外部额度，否则增加 worker 只会更快打满模型配额。

缩容需停止接任务、checkpoint 与 drain，满足终止宽限时间。HPA、集群节点容量和沙箱资源配额是不同层级。需要考虑预热、镜像拉取、存储挂载和依赖安装对首任务延迟的影响。

### Q43 MySQL MVCC 与任务状态 CAS 怎么结合

MVCC 提供不同事务隔离下的版本读取；任务状态更新可以用条件更新约束合法迁移，例如 WHERE id=? AND version=? AND status='RUNNING'，成功后 version 加一。并发失败方重新读取，不覆盖新状态。

InnoDB 的一致性快照读、当前读和锁定读行为不同，不能只说“可重复读解决所有幻读”。结合索引、next-key 锁、执行计划和隔离级别分析。跨外部工具的效果不会因本地事务回滚自动撤销。

### Q44 Redis Lua 的原子性等不等于失败回滚

不等于。脚本执行期间其他命令不会插入它的中间过程；运行中报错时，之前已经完成的写入并不会自动获得关系数据库式回滚。先验证类型与前置条件，减少部分写后失败窗口；关键账本放在具有相应事务能力的系统里。

Redis Cluster 中一个脚本涉及的 keys 通常需要落在同一 hash slot，可用 hash tag，但要防热点。长脚本会阻塞其他请求，重操作应拆解或换系统。参考：[Redis Lua 执行语义](#cite-23)。

### Q45 语言基础应该复习哪些

| 主语言 | 优先问题 | Agent 场景关联 |
| --- | --- | --- |
| Go | context、goroutine、channel、mutex、map、GC、pprof、连接池 | 工具并发、取消、内存增长、锁争用 |
| Java | 线程池、Future、异常传播、虚拟线程、事务代理、JVM／GC | 异步工具、阻塞调用、事务失效、OOM |
| Python | asyncio、同步阻塞、GIL、进程、类型与依赖管理 | SDK 调用、工具执行、CPU 与 IO 任务分离 |
| TypeScript／React | Promise、AbortController、流式解析、状态同步、渲染节流 | run 时间线、取消、断线重连、长输出渲染 |

掌握主语言，再补 SDK 常用语言；不要为了“全栈”把四种语言全部从头学。投桌面岗位补 IPC、主进程／渲染进程隔离、文件权限、自动更新及崩溃恢复。

### Q46 Transformer 和采样参数需要讲多深

能解释 token、embedding、注意力、位置编码、上下文长度，以及 prefill 与逐步生成的区别。标准稠密注意力的计算随序列长度增加，长上下文也增加缓存与延迟成本；上下文装得下不代表一定利用得好。

temperature 调整分布，top-p／top-k 限制候选。低温不保证系统完全可重复，也不消除知识或工具错误。输出截断、拒绝与结构化响应要按 API 的终止原因处理。Agent 工程岗先掌握这些，再按 JD 决定是否深入推理引擎。

### Q47 RAG Prompt 与微调怎么选择

新鲜或需要溯源的知识，优先检索；工具用法、任务边界和结构化输出先优化 Prompt 与工具接口；稳定行为、格式和领域能力在有高质量数据时考虑微调。它们可以组合。

先做失败归因和小规模基线，不要一上来用训练解决索引错误或权限问题。微调后仍需独立评测、分布外测试、工具兼容和上线回滚。框架选型也要围绕需要的控制、持久化和调试能力说明，不能只说“生态好”。

### Q48 SFT LoRA DPO 和 RL 需要掌握什么

SFT 从示范数据学习目标行为；LoRA 是参数高效适配方法，并不是新的业务训练目标；DPO 利用偏好对进行优化；RL 用奖励信号优化行为。对工程候选人，更关键的是任务数据、工具轨迹、环境、奖励与评测如何接起来。

Coding 训练要关注测试泄漏、奖励投机、轨迹质量与失败样本。代码通过测试但删除测试、硬编码答案或越权读取参考解，都可能是“奖励高但不可接受”。只有目标岗位强调后训练或算法，才把损失函数推导和训练稳定性细节放入主线。

### Q49 Agent 模型怎么选 如何 fallback

用目标任务集比较工具调用可靠性、代码或文档质量、长任务稳定性、上下文需求、时延、成本和配额。按任务阶段选模型可能节省成本，但需要验证阶段切换的信息传递与整体质量。

不同模型对工具 schema、并行调用、消息格式、缓存与停止原因的支持可能不同，建立适配与契约测试。fallback 改变模型不一定能解决检索或工具故障；副作用未确认前换模型重跑会放大重复执行风险。

### Q50 如何评价 Qoder WorkBuddy 和相近产品

用可复现任务比较，不背宣传词。记录产品版本、模型、允许权限、总预算和验收规则，选择跨文件修复、失败恢复、长任务、代码知识更新、文件报告与受限工具操作等场景。

评价维度包括定位正确性、自主完成程度、验证质量、恢复、可控性、时延和成本。若产品内置模型无法统一，比较的是端到端产品体验，不能把差异归因于 Harness。准备一张“观察 → 可能原因 → 验证实验”的表，不猜测内部实现。

**核心对象**：run 固定任务、仓库版本与配置；workspace 保存基准 commit 及工作树改动；step 保存决策和证据；operation 管工具副作用；artifact 保存补丁、日志和验收结果。

**检索**：文本找入口，符号／调用关系扩展，语义检索补充业务表述；所有证据落到文件、行号和版本。对未提交修改建立覆盖层，不能靠旧索引推断当前代码。

**执行**：在隔离工作树修改，工具有路径与资源约束。先理解已有测试，再修复并做针对性回归；验收器从干净基准应用补丁，检查测试、越界改动和是否篡改验收条件。

**恢复**：每步落事件与 checkpoint；worker 换人继续时加载补丁和状态，先解决未决动作。取消后阻止新调用，保留已生成产物。到预算仍未完成，就提交明确的部分结果与失败证据。

**容量推演**：稳态下并发约等于每秒新任务数乘平均活跃时长；再考虑峰值、排队和资源差异。可用 Little 定律估算，不能把平均值当峰值容量。

**指标**：任务验收通过率、漏改／回归、P95 总耗时、沙箱就绪时间、人工接管和单位成功成本。

**加压追问**：多个任务同时改同一仓库怎么办？隔离 workspace，基于基准版本交付补丁，合入前冲突检测；不能让共享目录承担隐式合并。

### D2 设计读取资料并生成周报的 WorkBuddy 类办公 Agent

**练习任务**：读取有权限的文档、表格和会议材料，形成带证据的周报；用户还可能要求通过聊天工具发送。

将目标拆为获取材料、抽取事实、组织内容、生成产物、校验和发送。资料可以并行读取，跨来源事实冲突保留来源和时间。对文档与表格使用确定性解析，模型负责归纳表达，数字回到原始单元格或记录复算。

**权限**：连接器身份与用户身份绑定，凭据由代理按作用域注入；模型不需要拿到原始密钥。读取权限和发送权限是两件事。外部资料中的指令不能扩大授权。

**产物验证**：核对引用、日期、统计口径、重复与缺失；表格检查公式或数值；生成文件不仅要能打开，还要检查版式和主要内容。数据缺失时标识缺口，不补造数字。

**发送**：先形成可以审核的内容，再遵循产品要求取得必要确认。发送操作使用稳定 operation_id；超时后查结果，避免重复发送。编辑周报完成与消息成功送达是两个状态。

**追问**：最慢来源超时是否整体失败？看是否属于关键数据；允许部分交付时标识时效和缺失，不能让缺失数据悄悄变成零。

### D3 把本地 Agent 改造成企业多人使用的云端平台

**控制平面**管理身份、租户、Agent 定义、版本、权限、任务、资源与审计；**执行平面**运行模型循环和工具，利用隔离沙箱访问受授权资源。消息渠道映射到独立用户或群会话，不能用“同一个机器人”推导所有人共享上下文。

把 Agent 配置、Session 历史和 Runtime 资源分开。Runtime 不应因为聊天记录保留就永久占用计算资源，Session 也不应因沙箱被回收就失去任务状态。这与腾讯公开文档的对象划分相对应，但此处是练习架构。[T2 企业智能体对象](#cite-5)。

**专享交付**：明确客户网络、模型出口、依赖镜像、持久化、更新渠道与审计要求。离线或受限网络需要预置依赖和升级包，不能默认执行时可访问公网。

**升级**：部署版本、工具和数据 schema 一起考虑；新 run 用新快照，旧 run drain。客户环境不同，通过契约测试和兼容矩阵确认，而非每次人工复制配置。

**追问**：共享沙箱池如何确保干净？验证文件、进程、网络连接、缓存、卷和凭据生命周期；清理无法证明时销毁重建或使用更强隔离。

### D4 设计多模型调用与额度平台

任务入口先鉴权和校验预算，经租户公平调度进入 worker；worker 每次模型调用还需经过模型 QPM／TPM／并发准入。配置版本与调用记录关联，成本按实际 usage 结算，异常有追踪与对账。

以“10 个任务／秒、平均每任务 6 次模型调用”为假设，模型需求约 60 次调用／秒，即 3600 QPM；实际峰值受任务步骤节奏影响，不能平均摊平。TPM 还需按每次输入／输出与提供商口径计算，缓存命中也不一定抵扣相同的额度。

队列给出等待和取消状态；预计无法在 deadline 内完成时进行明确拒绝、降级或让用户选择。调度避免高优任务永久饿死普通任务。fallback 应记录原因，检验 schema 兼容，并保证未确认的工具写入不因模型切换重复发生。

**追问**：服务端熔断后已有任务怎样处理？新调用按策略准入，正在执行的调用等待结果或安全取消；入队任务保留原始身份和预算，恢复时重新校验额度。

| C4 流式事件解析与重连 | 增量文本、完整工具参数、事件去重 | JSON 跨分片、UTF-8 字符跨字节、半路断线、重复终态 |
| C5 租户公平限流队列 | QPM、token 预算、优先级、公平与 deadline | 大任务霸占、取消退款、估算偏差、429 重试风暴 |
| C6 代码知识增量索引 | 内容哈希、变更检测、删除与版本快照 | 分支切换、未提交修改、重命名、部分构建失败 |
| C7 上下文压缩器 | 保留约束与未决步骤、摘要事件版本 | 过时异步摘要、tool 配对、用户纠正、目标变化 |
| C8 任务评测器 | 固定环境、隐藏验收、按切片统计 | 超时、作弊修改测试、评审器异常、case 本身不可解 |

**C2 和 C3 联合验收**：在“写执行意图之后”“外部动作之后”“结果落库之前”三个位置主动模拟崩溃，恢复后检查实际业务效果。目标不是每次都自动成功，而是在无法确认时正确停留于 UNKNOWN。

**C4 联合验收**：流式重连不能再次启动整个业务请求；如果服务只恢复文本却丢失了完成产物，不能算完整恢复。

### 10 2 算法训练清单

| 类型 | 代表练习 | 需要讲清楚 |
| --- | --- | --- |
| 哈希与滑动窗口 | 无重复最长子串、最小覆盖子串 | 窗口不变量、重复字符、空输入 |
| 区间 | 合并区间、插入区间 | 排序、重叠规则、边界相等 |
| 链表 | 反转、环检测、回文链表 | 空链表、奇偶长度、是否恢复链表 |
| 树与图 | 层序遍历、最大路径和、拓扑排序 | 负值、环、节点依赖 |
| 堆与缓存 | Top K、LRU | 复杂度、更新旧键、容量边界 |
| SQL | 分组 Top N、最新记录、游标分页 | 并列、空值、索引与稳定排序 |

这些是基础能力训练清单，不是对目标公司出题频率的统计。一般每天 1 道中等题加 1 道旧题复述；写出正确解后解释时间／空间复杂度和关键边界。社招高级岗仍要保证能独立编码，不能从某份“无手撕”的面经推出不考算法。

## 11 项目复盘与表达材料

### 11 1 至少准备三个故事

**主项目 8 分钟**：最贴近目标岗位、你负责最深的系统。围绕真实业务任务和完整链路展开，具体指出自己做的模块、接口、数据结构与取舍。

**故障故事 5 分钟**：选一次影响明确的失败。讲异常现象、排除过的假设、定位证据、止损、修复、验证和长期改进；能在白板画出故障时间线。

**优化故事 5 分钟**：讲原始瓶颈、测量方法、改变哪一变量、代价和上线结果。不要把更换模型、缩短请求、减少任务难度同时发生后的提升全部归功于一个改动。

若做过模型接入、额度或路由，可以用 Q35、Q40、D4 整理；若做过有副作用的订单／发券／消息任务，可以把本地事务、外部结果未知和恢复经验迁移到 Q05、Q39；若主要做业务后端，需要另补一个可运行的 Agent 项目，不能把常规服务包装成已有 Agent 研发经历。

### 11 2 项目一页纸模板

| 字段 | 应填写的内容 |
| --- | --- |
| 用户与目标 | 谁使用，想完成什么任务，失败有什么影响 |
| 规模与约束 | 用户／任务量、并发、时延、资源、数据与权限要求 |
| 我的职责 | 具体模块与独立决策，团队协作边界 |
| 基线 | 原系统或最简单方案，如何测量 |
| 架构 | 模型、检索、工具、状态、执行环境、存储、前端 |
| 关键选择 | 两个被放弃的方案及理由 |
| 失败边界 | 超时、重复、取消、升级、越权各怎样处理 |
| 评测 | 成功标准、样本来源、独立测试与错误分布 |
| 结果 | 实测数字、统计口径、时间窗和业务效果 |
| 局限与下一步 | 哪些场景尚未覆盖，怎么验证下一次改进 |

### 11 3 数字怎么讲得可信

不要只说“成功率提升 10%”。应说明从 a% 到 b%，是提升 b−a 个百分点还是相对提升；分母是任务、调用还是用户。失败、取消和超时是否纳入，必须一致。

“平均成本下降”还要看任务难度、缓存、模型组合与多次重试。可以使用：**成功任务单位成本 = 所有尝试的总成本 ÷ 验收成功任务数**。失败尝试的成本不能悄悄移出分子。不要把本地测试通过、发布成功或 endpoint 正常当作业务收益的证据。

未真实测过，就说尚未测量并提出测法。示范项目可以给实验结果，但必须注明是本地测试而非生产规模。

### 11 4 90 秒自我介绍模板

“我主要做【技术栈／领域】，过去【年限】集中在【两类能力】。最相关的项目是【项目】，服务【用户和任务】，我负责【明确模块】。其中最有挑战的是【问题】，我通过【机制】解决，并用【评测或线上指标】验证结果。

我希望做 Agent 工程，尤其关注【代码理解／Runtime／企业工具】。我的优势是【真实可证明经验】，目前也用【自己的小项目或实验】补齐了【能力】。我比较看重任务从规划、工具执行到验收的整条链路，因此希望在你们【具体岗位职责】上继续深入。”

不要照念占位符。准备 30 秒、90 秒和 3 分钟三个版本，分别适应追问和打断。

### 11 5 两个能展示判断力的回答例子

**模型和框架有什么优势**：“我会先固定目标任务和验收标准。模型相同的情况下，重点对照检索定位、工具契约、恢复和验证；模型不能统一时，我只比较完整产品体验，不把差异直接归因于框架。做过的实验里，我能解释某个失败怎样被修复，以及它对成本和时延的影响。”

**做过一个高成功率 Agent 吗**：“我负责的是【范围】，成功指【验收条件】。在【数据集与样本量】上结果为【真实指标】，主要失败集中在【类别】。我们针对【机制】改进后在同一测试集复测，并观察【线上指标】。目前仍有【边界】，如果接入真实写工具，需要补上【恢复／权限／幂等】。”

### 13 1 Qoder Coding Agent 路线

## 14 面试前的一页速查

### 14 1 十个容易失分的说法

| 容易失分 | 应该补充的边界 |
| --- | --- |
| 没有工具调用就是成功 | 检查终止原因、产物和任务验收 |
| 框架 checkpoint 保证只执行一次 | 外部动作还需幂等、查询与未知结果处理 |
| 工具超时就重试 | 区分读取和已产生副作用的写入 |
| 向量库就是长期记忆 | 定义记忆类型、作用域、更新、冲突与删除 |
| 长上下文解决所有问题 | 看相关性、噪声、成本和事实时效 |
| 缓存命中率高所以快 | 分开看命中 token、prefill、decode、工具与总耗时 |
| JSON 合法所以动作安全 | schema 之外还有权限、路径和业务条件 |
| Redis Lua 原子所以会回滚 | 原子执行与失败回滚是不同语义 |
| 增加 worker 就解决限流 | 下游 QPM／TPM／并发和公平调度仍可能限制 |
| Agent 自测通过就完成 | 独立验收最终产物与业务效果 |
