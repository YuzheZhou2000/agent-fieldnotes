## 新问题不是有没有点击批准

一个 Agent 计算无误、引用真实、执行前也得到批准，仍可能替用户决定了“应该优化什么”。例如部署评审同时面对成本、可用性和回滚复杂度：选择哪个指标作为主目标，不是单靠测试通过就能回答的问题。如果 Agent 先定义指标，再准备证据，最后让人点确认，审批记录可能完整，却没有说明关键取舍如何形成。

Anthropic **2026 年 10 月 27 日**发表的专家判断研究把关注点从“人是否识别错误答案”移向“多个合理选项之间，Agent 的倾向如何影响选择”。50 名使用 AI 的因果推断分析师在合成农业任务中使用 Claude Code / Opus 4.8 High；Agent 被随机指定隐藏的建议方向，并要求诚实论证。研究不是生产部署普查。<sup><a href="#cite-1">[1]</a></sup>

本文于 **10 月 28 日核查**。下文先限定证据，再给出原创工程设计；没有独立复现，也没有证明任何界面或审批方案已经消除影响。

## 先看估计量，再谈影响

论文 Table 2 区分两类结果，不能将它们都写成“专家被说服比例”。<sup><a href="#cite-2">[2]</a></sup>

| 估计对象 | 作者报告 | 不能怎样解释 |
|---|---|---|
| 四项分析选择的随机建议方向差异 | 调整后 0.72，95% CI [0.60, 0.83]；合并 n=195 次选择 | 不是 195 名专家；解释为个体翻转占比还需无逆反假设 |
| 最终政策建议的平均分数差异 | 调整后 0.17，95% CI [-0.06, 0.40]，单侧 p=.069 | 分数为停止=0、延期=.5、推广=1；不是推广概率增加 17%，主分析不显著 |

登记时已有 17 人开始任务、其中 4 人退出，不能写成招募前完整预注册。一个任务、一个模型及人为强化的建议倾向限制了外推；自选不用 AI 的对照也不能证明因果生产率收益。<sup><a href="#cite-2">[2]</a></sup>

对开发者更有用的问题不是寻找一个“影响率”放进风险面板，而是确认自己的产品把哪些未定取舍交给了模型：目标定义、样本排除、权重、容忍阈值，以及哪些选项根本没有进入用户视野。下面是由这些问题引出的工程建议，不是论文已验证的缓解措施。

## 三层合同：正确、获准、由谁取舍

| 层次 | 要回答的问题 | 可留存证据 | 单独不足以证明什么 |
|---|---|---|---|
| 事实与实现 | 数据、计算、代码是否支持陈述？ | 数据版本、测试、产物、来源 | 目标或价值排序适当 |
| 行动授权 | 谁允许对什么资源做什么？ | 身份、范围、确认、有效期 | 用户独立形成了目标 |
| 判断形成 | 关键取舍从何而来，用户认可什么理由？ | 替代方案、约束、先验、最终理由 | 决定一定正确或完全不受影响 |

[交付证据合同](agent-proof-contracts.html)处理第一层与完成证明，[权限与隔离](agent-containment.html)处理第二层。第三层不能仅靠再弹一次“确认”补齐。它也不要求人拒绝 Agent 的好建议：主动接受有依据的修正，与不知情地继承默认目标，是不同的产品行为。

实际系统应先区分**可验证事实**和**需要用户取舍的变量**。例如“方案 A 每月成本更低”是待核实的事实；“优先最低成本，即便恢复更慢”是目标选择。让模型输出一个 decision point 列表供业务逻辑筛选，比允许它自行决定何时需要审批更易审计；但列表本身也可能遗漏，因此不能成为唯一发现机制。

## 一个最小决策记录

以下是设计草案，不是新增协议，也不是生产实现。它只记录必要的可见决策材料，不要求收集模型隐藏推理或用户敏感画像。

```json
{
  "decision_id": "deploy-review-42",
  "question": "本次部署优先成本还是恢复时延？",
  "constraints": ["不能改变数据保留政策"],
  "user_initial_position": "尚未决定",
  "alternatives": ["较低成本", "较短恢复时延", "先补充证据"],
  "agent_recommendation": "较短恢复时延",
  "evidence_refs": ["artifact:load-test-v3"],
  "selected_option": "先补充证据",
  "user_reason": "缺少故障恢复测量",
  "status": "needs_evidence"
}
```

**实现取舍**：记录应和任务、产物版本绑定，但不要把它当成可直接执行的授权令牌。最终方案改变时，旧确认不能自动覆盖新行动；先验未填写应保留“尚未决定”，不要由 Agent 替用户补出意见。理由可以简短，也可以明确为“授权 Agent 在这些约束内代选”，这比假装每一步都经过独立审议诚实。

例如成本优先的用户在看到恢复测试后改选高可用方案，系统应保存新证据与修改理由，而不是把“坚持原意见”当成功指标。反过来，如果用户未看到另一个方案，只对模型推荐点了同意，也不能由日志推断其真正比较过两者。

## 界面顺序也是实验变量

可以为高影响、低可逆的决策比较两种流程：

1. **先征询约束，再给建议**：先问不可牺牲的条件及尚未确定的部分，随后展示建议和有实际意义的替代方案。
2. **先建议，再要求比较**：给出建议时同时标出依赖的假设，允许用户查看“另一方案在什么条件下更好”，再做选择。

两者均可能失败。第一种增加负担，也可能把用户过早锁在缺乏信息的立场；第二种更省时，但首个框架可能压缩后续比较。对低风险可逆任务逐项询问会制造审批疲劳；对高风险任务只展示“推荐 / 不推荐”则可能隐藏真正的价值冲突。不要以形式上的对称文案替代实质不同的选项，也不要为制造平衡而给明显错误的方案同等地位。

多 Agent 评审也不是天然独立。若两个 reviewer 接收同一个已经定型的目标、同一份摘要和同一候选清单，它们最多独立检查执行，未必独立检查问题设定。可以分开任务：一个核对事实，一个显式寻找遗漏约束；这仍需评估，不能把“两个模型同意”当成用户判断的替代品。

## 如何评测，而不把不服从当成目标

建议先在无真实外部副作用的沙盒任务上设计研究，并取得参与者对实验与记录的适当同意。不要在真实生产决策中秘密植入倾向来制造指标。以下评测方案**未执行**：

| 观察项 | 建议对照 | 防止的误判 |
|---|---|---|
| 事实与任务质量 | 相同任务、证据及预算 | 为减少影响而牺牲正确性，却宣称总体更安全 |
| 取舍可见性 | 检查是否识别关键假设和遗漏选项 | 只会复述推荐，不理解它依赖什么 |
| 合理修正能力 | 提供真正改变结论的新证据 | 将坚持原意见误作独立性 |
| 决策可追溯性 | 对照实际展示材料与最终理由 | 决策后由模型编写一份漂亮的合理化记录 |
| 交互成本 | 耗时、中断、放弃及无差别确认 | 更多审批界面造成更少实际审阅 |

固定任务难度和界面材料，预先说明主要指标与排除规则。将同一参与者的多次选择视作相关观测，不把每次点击当成独立的人；按任务类型报告，而不是产出一个“人类自主性分数”。事后理由也不是思想来源的无误测量，最好同时保留实际显示的选项和时间顺序，以便检查记录与交互是否相符。

## 对专业开发者的行动边界

短期内最值得做的是盘点：哪些产品默认值实际承担了价值选择，哪些自动摘要省略了重要替代方案，哪些审批只发生在目标已经被模型固定之后。把这些位置标为决策边界，与已有工具权限和交付验收并行维护。

不要用这项研究断言专家普遍失去判断，也不要从最终政策主分析不显著推出人类监督已经可靠。它提示的是一个需要独立测量的层次。工程上可先交付清晰的决策记录与版本绑定，再用受控评测判断额外交互是否值得，而不是直接把未经验证的流程包装成防护。
