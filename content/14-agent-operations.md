## 从一个能跑的循环，到一项有人负责的服务

一个工单 Agent 在开发机上能读资料、生成回复并完成登记。上线以后，同一租户突然提交一万条工单，模型接口开始限流；部分消息已发出但回执丢失；值班人员按下停止，旧 worker 却还在处理；发布回滚以后，昨日批准的批次仍然等待恢复。此时，继续优化提示词无法回答最紧急的问题：哪些请求已经被接收，哪些动作仍可能发生，谁负责把未知结果查清？

本文沿一个**虚构的多租户工单服务**设计运营合同，不提供可直接部署的实现。目标是把单次循环放进长期运行的系统：入口负责接收边界，调度器负责容量，持久账本负责事实，执行器负责受控动作，验收与值班流程负责收尾。下面的字段、阈值选择和演练都是工程建议，未在真实客服系统上执行，也没有调用模型或发送工单消息。

[执行循环基础](agent-loop.html)已经解释策略、授权、执行和停止；[长任务状态](claude.html)解释检查点与恢复。本篇不再展开 SDK 的内部恢复机制，而关注多个任务、多个 worker、外部服务和人的共同运行边界。

| 容易被当作成功的信号 | 它实际证明了什么 | 仍需建立的事实 |
|---|---|---|
| 请求返回已接收 | 服务按约定接纳了任务 | 是否已持久化、何时开始、能否按期交付 |
| 队列消息被消费 | 一次投递到了某个消费者 | 是否完成业务动作、是否会再次投递 |
| trace 显示工具成功 | 采集到了一个诊断事件 | 外部写入的权威结果和任务验收 |
| 模型建议批量关闭 | 策略给出了一个候选动作 | 当前主体是否批准了这些对象与参数 |
| 停止调度 / 回滚发布 | 后续派发或版本选择被改变 | 已发出的动作、未知结果和补偿责任 |

## 入口合同：先保证接收，再讨论执行

### 给任务一个稳定身份

对异步接口，建议返回稳定的 `task_id`、当前状态和查询入口，并明确“已接收”是否意味着持久接收。客户端重试提交时带自己的请求标识；服务按租户与请求标识去重，同一标识对应不同目标或参数时拒绝混用。一次提交可以产生多次 worker 尝试，但不应因此变成多个业务任务。

“写任务记录”和“投递队列”若是两个独立写操作，就存在双写裂缝：先记账再投递可能留下永不执行的任务，先投递再记账可能让 worker 找不到合同。一个常见设计是把任务和待投递 outbox 记录放进同一数据库事务，提交后才返回持久接收；独立 dispatcher 反复扫描 outbox 并投递。这里的 outbox 是**设计选项**，不是本站实现，更不让数据库和外部队列凭空共享事务。

dispatcher 可能在投递成功、标记完成之前崩溃，所以下游仍要接受重复消息。队列消息宜只携带任务 ID、预期版本与必要路由信息，worker 再从权威存储加载合同；消息里的旧参数不能覆盖新目标。对选定队列，还必须查清可见性超时、确认、保留期、延迟投递与死信语义，不能只看到“可靠队列”四个字便推断端到端 exactly-once。

### 控制入口和在途量，而不只限制 worker 数

Google SRE 的过载章节指出，不同请求的资源代价差异很大，单看 QPS 容易误判容量；它讨论按客户限额、资源信号和客户端节流处理过载。<sup><a href="#cite-1">[1]</a></sup> 对 Agent 的下面这组控制是本文的延伸，不是 Google 测过的 Agent 参数。

| 边界 | 建议限制 | 不限制时的后果 |
|---|---|---|
| 租户入口 | 待处理任务数、提交速率、总预算预留 | 一个租户把队列与账本撑满 |
| 全局调度 | 活跃任务、模型并发、工具并发、沙盒时长 | worker 很多，真正依赖仍然拥塞 |
| 单任务 | 总 deadline、最大尝试、模型与工具预算 | 一个循环长期占用共享资源 |
| 重试通道 | 重试令牌、最大延迟、可重试条件 | 错误触发更多流量，挤掉正常任务 |
| 核对通道 | 独立容量、查询速率和升级时限 | 停止写入后，连未知结果也无人查清 |

入口按已知成本预留只是估计，运行中还要结算实际消耗，并在下一动作前检查剩余预算。模型 token 限额、下游工具速率和浏览器会话上限是不同瓶颈，不能全部换算成“每秒多少任务”。人类审批等待应释放可释放的计算槽位；恢复时再竞争资源，而不是无限占着一个 worker。

调度可先用按租户分队列的轮转与有界并发，避免大客户占满共享队列。优先级由受信入口按合同确定，不能让工单正文写一句“紧急”就获得高优先级。长短任务混排会导致队首阻塞；拆分队列能改善隔离，也增加容量分配与饥饿治理成本。具体算法要用自己的任务长度分布验证。

### deadline 必须覆盖排队和收尾

只给模型调用设 60 秒超时，不能保证任务在 60 秒内交付。本文建议同时记录入口时刻、首次派发、审批等待、工具等待、最终验收与核对完成时间。每次派发前检查剩余 deadline，并为验收和必要核对留预算；过期任务不要继续排队等待“最终总会轮到”。

队列长度相同，最老任务已经等待多久可能完全不同。至少并列查看等待年龄、deadline 违约数、租户分布与预计剩余工作量。取消或 deadline 到期后，停止新增业务动作，但已经派发的动作仍要交接；核对可以在单独的收尾时限内继续，不能把任务取消解释成所有远端操作都已取消。

## 运行账本：任务、尝试与外部操作分开编号

### 三种 ID 对应三种问题

以下字段是教学模型，不是某个框架的标准 schema。权威存储可以采用事件追加与投影，也可以采用带版本检查的事务表；关键是并发修改与恢复合同能够被检查。

| 记录 | 核心字段示例 | 要回答的问题 |
|---|---|---|
| Task | `tenant_id, task_id, request_key, goal_version, deadline, release_id, terminal_reason` | 用户要完成哪一个目标，当前还允许做什么？ |
| Attempt | `attempt_id, task_id, lease_epoch, worker_id, started_at, ended_at, outcome` | 哪一次执行持有调度权，为什么结束？ |
| Operation | `operation_id, task_id, target, payload_hash, approval_id, dispatch_state, effect_state, receipt_ref` | 哪一个具体外部动作被批准、派发、确认？ |
| Reconciliation | `operation_id, evidence_ref, observed_at, owner, next_check_at, resolution` | 未知结果由谁根据什么证据核对？ |

`task_id` 不随重试变化；每次执行尝试获得新的 `attempt_id`；同一个业务动作的安全重试复用 `operation_id`，改变目标或内容则重新形成操作与审批。摘要哈希可检测载荷是否变化，却不能单独表达业务意图：两次内容相同的通知可能是用户有意发出的两次动作，也可能是同一次重试。

AWS 的幂等 API 文章把调用者提供的请求标识、参数一致性检查和服务端原子处理放在一起讨论，并说明去重信息有保留期限。<sup><a href="#cite-2">[2]</a></sup> 本地建立 Operation 表只解决本地记账，不能证明第三方服务也能原子去重。上线前要确认对方是否接受该键、在哪个范围去重、保留多久、如何查询结果；超过窗口后不能按旧假设自动重试。

### 把调度状态和副作用状态拆开

只用 `running / success / failed` 容易掩盖两类事实。一个任务可以已经取消调度，同时仍有一个结果未知的外部写入；一次网络尝试失败，也可能完成了目标业务动作。

```text
调度状态：queued → leased → running → waiting / terminal
结束原因：succeeded / failed / cancelled / expired / exhausted

外部操作：prepared → dispatching → confirmed_applied
                              ├→ confirmed_not_applied
                              └→ unknown → reconciliation
```

这个拆分要求查询接口同时返回结束原因、未确认操作数和收尾负责人。只有产物验收达到合同条件，才能标记任务成功；`confirmed_applied` 也仅表示某一步写入发生，不表示整个任务成功。

在发网络请求之前持久化操作意图与 `dispatching`，能留下恢复入口；若进程随后崩溃，恢复者可能仍不知道请求是否离开本机。因此这个状态必须保守处理，不能把“没有回执”改写成“没有执行”。扫描器应寻找超时租约和长时间未收尾的操作，把它们放入核对队列，并保留原操作 ID。重新派发前还要排除旧 worker 或迟到请求继续提交的可能；无法排除且没有有效幂等合同时，人工接手也不能把当前未生效提升为安全重试的证明。

### 租约防并发，不能凭空撤销旧 worker

多个 worker 领取任务时，可用条件更新将版本与 `lease_epoch` 一并推进，后续账本写入都检查当前 epoch。旧 worker 的迟到结果只能作为待核对证据，不能覆盖新尝试的状态。

但租约过期并不意味着旧进程停止，更不意味着外部请求撤回。fencing token 只有在受保护资源也检查它时才能拒绝旧写入。若第三方 API 不理解 epoch，本地“重新检查租约”与远端提交之间仍有竞态；需要受控出口、对方幂等合同或保守的人工核对来降低风险，不应宣称仅靠分布式锁已实现 exactly-once。

## unknown 是工作队列，不是一个被遗忘的错误码

AWS 的超时与重试文章强调，超时不证明副作用没有发生，重试还可能放大过载；退避与抖动用于控制重试流量。<sup><a href="#cite-3">[3]</a></sup> 在 Agent 服务里，恢复决策还要绑定当前权限、操作身份和任务 deadline。

| 观察 | 下一步建议 | 不应直接做什么 |
|---|---|---|
| 外部操作查询确认已生效 | 保存回执，进入产物验收 | 再次发送同一业务动作 |
| 已确认未生效且原派发不可能再生效；或仍受有效的服务端幂等合同保护。两种情况都要求错误可恢复 | 检查审批、deadline、预算与重试次数，再有限重试 | 把当前未查到结果当作旧请求永远不会生效 |
| 查询暂时查不到 | 检查一致性与查询窗口，继续核对或升级 | 把一次空查询当作未执行证明 |
| 已无法查询或证据冲突 | 保持 unknown，交给指定负责人 | 为了清空队列猜测成功 / 失败 |
| 目标或文案已变化 | 建新版本并重审未执行部分 | 用旧幂等键承载新意图 |

核对任务本身也要有截止与升级路径。可以设置“多久必须开始核对”和“多久仍未知必须人工接手”，但人工接手不自动等于 unknown 已解决。账本要记录最后查询时间、证据、下一动作和负责人；运营看板应显示最老 unknown 的年龄，而不只显示总数。

重试尽量由明确的一层统筹。若网关、SDK、worker 与任务调度各自重试，会叠加请求量，并让预算统计失真。需要清点各层实际尝试次数，在重试预算里计入这些请求。恢复时也要检查原审批是否撤销、参数版本是否变化；曾经批准过，不代表今天可以继续执行任意遗留工作。

## 观测闭环：从用户结果定位到一次派发

Google SRE 将用户可见的黑盒结果与内部白盒信号配合使用，并提出时延、流量、错误、饱和度四类信号，区分成功与失败请求的时延。<sup><a href="#cite-4">[4]</a></sup> 对 Agent，可在这个基础上定义自己的服务指标，避免只看模型首 token 延迟和工具 HTTP 成功率。

### 先把分母写清楚

建议分别报告入口拒绝率、已接收任务按期验收成功率，以及终态任务的结束原因分布。第二项的分母可取某个接收时间窗口内、截至观察时刻已到约定交付期限的任务；分子只计这些任务中在各自期限内通过验收的任务。超期后才成功、仍等待或仍未知的任务均保留在分母，不能补入按期成功分子。尚未到期的任务单列，并区分已提前完成与仍在途。用户主动取消如何计入，必须在合同里预先定义，同时保留原始取消数。

如果只对已完成任务算平均时延，慢任务仍在队列里时看板会显得异常健康。除完成时延的分位数外，还要显示在途年龄和逾期比例。人审等待可从执行器效率指标中拆出，但用户看到的端到端耗时仍应包含它。对并行工具，阶段耗时可能重叠，不能把所有 span 的 duration 相加冒充端到端时延。

| 运营问题 | 建议观测 | 常见误读 |
|---|---|---|
| 是否真的交付 | 按期验收成功率、产物校验失败、人工接管 | 把模型回复完成当成交付 |
| 卡在哪里 | 排队 / 审批 / 模型 / 工具 / 验收 / 核对耗时 | 只测模型速度 |
| 是否失控 | 取消后新增派发、越过审批的动作、重复副作用、unknown 年龄 | 只看 5xx |
| 谁在占容量 | 按租户的在途量、重试量、资源与限额使用 | 用全局平均掩盖单租户饥饿 |
| 成本是否可持续 | 同接收批次全部成本、失败成本、核对成本、成功数 | 只除以成功调用或漏掉失败任务 |

这些是自定义设计指标，不是通用 SRE 标准或本站实测。告警应绑定有负责人、有处置步骤的影响：例如批准范围外派发属于安全异常，长时间积压的 unknown 需要核对接手；某个模型偶发慢响应可能只需进入趋势分析。阈值由任务风险、业务期限与正常流量建立，不直接照抄别人的百分比。

### trace 负责解释，账本负责恢复事实

把 `task_id / attempt_id / operation_id / release_id` 作为关联字段，让一次失败能从入口、队列、模型、工具一直定位到外部回执。记录采样、脱敏、导出失败和保留期；缺失 span 不能证明没有发生调用。关键审批和派发记录应在权威账本里持久化，不能依赖一个可被采样丢弃的观测 exporter。

这不意味着所有原文都应写入日志。工单正文、凭据和消息内容需要独立的访问与保留策略；诊断系统优先记录有权限控制的引用、版本和摘要。高基数操作 ID 适合用于日志关联与查询，不宜无边界地放进每一条时序指标标签。更详细的 trace 缺失与恢复边界见[长任务状态](claude.html)和[生产轨迹评测](agent-evaluation.html)。

## 事故处置：先缩小影响，再核对已经发生的动作

### 一个近期案例提供了哪些边界

xAI 官方于 **2026-10-20** 披露内部客服流程：IncidentWatch 每 5 分钟查看此前 15 分钟工单，由工程师判断是否事故；IncidentSweep 展示候选工单及精确文案供人批准，之后不再加票，小批执行、逐项记录，失败即停。<sup><a href="#cite-5">[5]</a></sup>

这份材料是厂商流程披露，不是公开实现、生产 SLA 或 exactly-once 证明。它没有让我们检查持久化、竞态和重试代码；也不能由单次案例推出通用吞吐或准确率。下面的批准合同与运行手册是**本文的工程推导**，不是对其私有实现的复原。

### 将事故确认和行动批准设为两个关口

“这些报告可能属于同一事故”是一项待核实的判断；“向这一批客户发送这段消息”是一项具有副作用的行动。检测器可以给出证据与候选集合，事故负责人确认影响范围，行动批准者再确认具体对象与内容。两者可以由同一个人承担，但账本里应是两种记录，不能因事故已经宣告就放开任意批量写入。

一个可审查的批次合同至少冻结：

- `batch_id / revision`：批准的是哪一版提案。
- 明确的目标 ID 集合及排除项：不把动态查询语句当作最终收件集合。
- 每个目标的精确载荷或不可变载荷引用及哈希：模板变量展开后的结果也需要落在批准范围内。
- 动作类型、租户、批准主体、有效期与政策版本：批准发消息不等于批准删工单。
- 每项独立 `operation_id`、批次并发上限和停止条件：恢复时能够定位到单项。

冻结集合限制的是上界，不强迫执行已经失去条件的动作。执行前若发现权限撤销、用户已退出、工单版本改变或事故结论修正，应停止或按合同跳过并记账；不能新增“看起来也相关”的工单来补足数量。集合或文案变更后创建新 revision，重新批准受影响的未执行部分。哈希只能检测差异，不能证明审批者身份与权限。

### 一份最小值班运行手册

| 顺序 | 操作 | 必须留下的证据 |
|---|---|---|
| 1. 定位范围 | 确认事故、租户、受影响版本和操作类别 | incident ID、证据、负责人 |
| 2. 限制新增影响 | 暂停受影响批次的新派发，必要时收紧入口 | 停止生效时间、epoch / 策略版本、仍在途清单 |
| 3. 保留核对能力 | 保持账本读取、回执查询与只读诊断可用 | 已确认 / 未执行 / unknown 三份清单 |
| 4. 决定处置 | 修复、回滚版本、重审剩余批次或申请补偿 | 处置批准和适用目标 |
| 5. 有界恢复 | 从已核对的逐项记录恢复，不从整批开头重跑 | 新尝试、复用的操作 ID、验收结果 |
| 6. 关闭事故 | 检查业务影响、遗留 unknown 和责任交接 | 结果清单、未解决事项、后续测试 |

按下停止时必须区分“请求停止”和“所有执行者已观察到停止”。已经通过出口的网络请求可能继续完成；并发批次也可能还有在途项。选择小批量只能限制风险暴露，不能撤销已经完成的消息。值班界面应给出确认的停止边界和仍可能生效的操作，不能只显示一个绿色的“已取消”。

下面是**串行批次的合同伪代码**。它展示检查点，不实现跨进程事务、权限校验服务或外部 API；不能直接作为上线代码：

```python
proposal = load_immutable_approved_revision(batch_id, revision)
for item in proposal.items:
    if stop_requested() or approval_expired_or_revoked(proposal):
        stop_new_dispatch_and_handoff_inflight()
        break
    operation = ledger.load(item.operation_id)
    if operation.effect_state == "confirmed_applied":
        continue
    if operation.needs_reconciliation:
        enqueue_reconciliation(operation)
        break
    check_current_permission_target_version_and_payload(item, proposal)
    if not initial_dispatch_or_safe_bounded_retry(operation, proposal):
        stop_batch_and_report_item_state(item)
        break
    # 原子检查操作状态、租约、版本、审批、deadline、预算和停止状态；
    # 成功时持久化本次派发记录及 dispatching，失败时不取得派发权。
    reservation = ledger.reserve_dispatch_if_current(item, proposal)
    if not reservation.granted:
        stop_batch_and_report_item_state(item)
        break
    outcome = dispatch_exact_approved_payload(
        item, operation_id=operation.operation_id
    )
    ledger.record_outcome_or_leave_recoverable_dispatching(item, outcome)
    if not outcome.confirmed_success:
        stop_batch_and_report_item_state(item)
        break
```

其中 `needs_reconciliation` 包括未知结果和没有收尾证据的派发；安全重试要求错误可恢复、次数有界，并满足以下之一：已确认未生效且旧派发不可能再生效；仍有有效的端到端幂等合同保护。每条派发记录关联 `operation_id / attempt_id / lease_epoch`，安全重试保持操作 ID 不变。

即使条件更新成功，停止标志和远端提交之间仍有窗口；外部幂等或出口 fencing 的支持范围要另外验证。批次剩余项不能因为“之前批准过整批”就绕过当前的撤销和到期检查。补偿动作也要单独定义权限与结果，不能将“回滚”作为不受约束的第二轮批量修改。

## 发布闭环：shadow、canary 与两种回滚

Google SRE 的 canary 章节将其定义为小范围、有限时间的变更部署和评估，并要求能分组、评价及接入发布流程。<sup><a href="#cite-6">[6]</a></sup> 对 Agent，变更对象不止代码。下面的发布包和观测要求是本文建议。

### 固定可追溯的版本包

至少记录模型标识、提示词版本、工具 schema、检索索引版本、权限政策、控制器、验收器与依赖版本。如果模型服务只提供会漂移的别名，保存实际可见版本信息并披露无法完全复现的边界。任务默认固定一个可解释的发布包，避免重试时一半步骤使用新策略、一半步骤仍按旧审批。

升级不只是切流量。旧账本 schema、待决审批与 checkpoint 是否可被新 worker 理解，需要兼容策略。最小方案可以是让旧任务排空、新任务使用新版本；确需迁移时显式写迁移记录并重验未执行动作。不能为了恢复任务，静默改写原来批准的语义。

### 从离线样本走到受控真实流量

1. 离线回放：固定任务与工具替身，测试候选版本的行动提案和控制分支。替身测试不能证明真实第三方的副作用语义。
2. Shadow：候选读取获准的样本，只生成提案，不获得生产写工具和写凭据。复制真实请求本身也要符合数据权限与容量预算；“不提交最终答案”不足以阻止工具写入。
3. Canary：选择有代表性、风险有界的租户或任务组，和 control 分开计量。不要把同一业务写入同时交给两组执行。
4. 扩大范围：达到预先定义的样本量、观测时长和质量门槛后再扩容。稀少但严重的未授权动作可立即阻断，不等待平均分变差。

观测至少包含按期验收、unknown、重复副作用、审批偏离、资源与成本。低流量 canary 的“零错误”不证明安全；任务类型不同也会制造假提升。长任务要等到验收与核对窗口成熟，不能在入口响应正常之后马上全量。若新策略触发更多人审，既要检查是否减少风险，也要检查人工队列是否已不可承受。

### 回滚代码与补偿业务写入分别处理

发布回滚可以让后续任务回到已知版本，并暂停候选版本的新派发。它不会自动删除已发消息、恢复已关闭工单或返还被占用的第三方资源。业务补偿需要知道实际发生的操作、是否支持逆操作、当前状态是否允许，以及由谁批准。

回滚后还应核对候选版本的在途任务、pending approval 和 unknown；旧版本未必能读取新 schema。恢复前确认兼容或隔离这些任务。真正的退出标准是后续行为受控、已发生动作有清单、未知项有责任人，而非部署界面已经显示旧版本。

## 演练：用故障把运营合同逼出来

以下是**建议执行、尚未执行的服务演练**。可以先实现可控的队列与工具替身，再在隔离环境注入故障。本站的执行循环实验室只模拟单任务，不覆盖此处的多租户、持久化或真实网络语义。

| 注入故障 | 应检查的断言 | 必须保存的证据 |
|---|---|---|
| 同一提交重复到达；同请求键换参数 | 一个任务身份；参数冲突被拒绝 | 请求键、任务 ID、冲突记录 |
| 任务事务提交后、队列投递前崩溃 | dispatcher 恢复投递；任务不静默消失 | outbox 与投递记录 |
| 投递成功后确认丢失；租约过期而旧 worker 仍运行 | 重复投递可处理；陈旧写入不能覆盖新状态 | 两个 attempt、epoch 与出口动作 |
| 外部写入成功但回执丢失 | 进入 unknown；核对前不盲目重发 | 操作 ID、远端回执与恢复决策 |
| 核对查询暂时返回空 | 不将最终一致性延迟误判为未执行 | 查询时间、接口一致性合同 |
| 单租户洪峰与下游限流同时发生 | 正常租户仍获得合同内资源；重试有界 | 分租户等待年龄、拒绝与尝试数 |
| 批次执行中撤销批准或修改工单 | 停止后续派发；保留在途与已完成项 | 停止边界、载荷版本、逐项结果 |
| exporter 中断或采样丢失 | 仍能从账本恢复关键事实；暴露诊断缺口 | 账本与导出失败记录 |
| 新版本中途回滚，遗留新 schema / 审批 | 隔离或显式迁移；没有静默改写动作 | release ID、兼容检查、恢复记录 |

每次演练固定输入、版本包、故障点和验收器；重复运行并报告通过、失败和未覆盖项。除最终任务结果，还要核对外部动作集合、重试上限、租户隔离和 unknown 收尾。若替身只在内存里去重，不能将测试结果解释成数据库崩溃或第三方幂等已经验证。

## 上线前能否回答这七个问题

1. 返回“已接收”时，哪份持久事实已经存在，投递失败由谁补上？
2. 一个租户耗尽配额后，其他租户、核对通道和验收是否仍有资源？
3. 同一次业务动作重试时，哪些 ID 保持不变，外部去重窗口是否足够？
4. 任务停止后，哪些操作仍可能生效，unknown 由谁在什么期限内核对？
5. 批次批准是否绑定对象、文案、版本和主体，恢复时是否重新检查撤销？
6. 能否从用户可见失败定位到版本、尝试、动作与权威回执，而不依赖完整 trace？
7. 回滚版本后，谁负责已发生的业务写入和不能被旧版本读取的在途状态？

本篇为[学习地图第九站](../learn.html#operations)建立服务化基础入口，不表示运维方向已经完整覆盖。生产队列选型、多地域恢复、数据库迁移实作、SLO 与成本治理、真实故障注入仍需独立专题。继续阅读[系统设计](agent-engineering.html)、[执行循环](agent-loop.html)与[评测合同](agent-evaluation.html)，把单任务控制、服务运行和产物验收连起来。
