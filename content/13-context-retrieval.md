## 从一次找错文件开始

用户要修复 `parse_invoice` 对退款金额的处理。检索返回了三份名字相似的文件：当前实现、旧版本示例、另一租户的接口说明。即使它们都在向量空间里“很相关”，只有部分证据适合进入本次决策。最终补丁失败，可能发生在资料可见范围、候选召回、版本过滤、上下文装配或代码生成阶段。

本文建立一条可逐段检查的基础管线。例子与预算数字均为**教学假设**，没有训练 embedding、请求模型或执行检索基准；不是本站真实仓库的测量结果。读完应能解释：检索器找到什么、模型实际看见什么、答案用了什么，为什么需要三份不同的记录。

## 上下文、检索、记忆与缓存各有职责

Anthropic 的上下文工程文章把问题放在每轮推理的工作集上：维护指令、工具、外部资料和历史的选择，并讨论按需读取、结构化笔记与压缩。它提供工程经验，不给所有任务通用的最优 token 配方。<sup><a href="#cite-1">[1]</a></sup>

| 对象 | 解决的问题 | 一个容易混淆的边界 |
|---|---|---|
| 上下文 | 这一轮可见的信息与约束 | 存在数据库里不等于已进入本轮 |
| 检索 | 从候选集合中找相关证据 | 找到片段不等于正确引用或使用 |
| 持久记忆 | 后续任务可恢复的事实或经验 | 保存过不等于仍然有效或有权读取 |
| 缓存 | 复用已经计算的内容或结果 | 命中旧结果不等于满足当前版本与权限 |

这是本文的工程划分。基础教程先关注一次任务中的证据流；策略训练与跨任务记忆见[Agent 记忆专题](agent-memory.html)，压缩和待决调用保全见[长任务状态](claude.html)。不要先引入一套“长期记忆”来掩盖当前检索管线没有测清的问题。

## RAG 是检索加生成的一种组织方式

2020 年的 RAG 原始论文结合参数化生成模型与非参数化检索记忆，论文具体实现使用 Wikipedia 的稠密索引。今天工程中常把“先检索，再把证据交给模型”也统称 RAG；这类应用不一定实现了论文的训练和概率模型。本文只核查原始 v1 摘要中的结构，不宣称复现原论文。<sup><a href="#cite-2">[2]</a></sup>

基础管线可以拆成两条路径：离线将资料解析、切分、附上元数据并建立索引；在线把问题转成查询，在授权范围内召回候选，再过滤、重排、装配上下文、生成并验收。源文变化会使索引陈旧，在线查询也可能表达不出用户真正需要的证据，两边都要留诊断入口。

```text
源文 + 版本 + 权限 → 解析 / 切分 → 稀疏或稠密索引
                                           ↓
任务与约束 → 查询 → 授权候选 → 召回 → 重排 / 去重
                                           ↓
                              证据预算 → 本轮上下文
                                           ↓
                              生成 → 引用 / 产物验收
```

## 切分之前先定义证据单元

固定长度窗口容易实现，但可能切开函数签名与实现、表头与数据、结论与适用条件。按章节或语法切分能保留结构，却会产生长度很不均匀的块。重叠窗口可以缓解边界丢失，也会增加索引体积和重复候选。不存在可脱离任务直接照抄的最佳 chunk 长度。

对示例仓库，一个证据记录可包含 `document_id`、`chunk_id`、`commit`、路径与行段、所属主体、更新时间和内容哈希。文档 ID 保持来源可追溯；chunk ID 表示某个版本下的片段；更新后不能把旧行号无条件指向新内容。表格、日志与代码的解析规则也应分开版本化。

权限过滤应进入检索和读取边界，并在返回结果前检查当前权限。仅在最终回答中隐藏不该出现的文字，无法撤销已经暴露给模型的资料。若使用共享索引，要单独设计租户隔离、缓存键和权限变化后的失效规则。这些是实现责任，不能由“向量检索很相似”替代。

## 稀疏与稠密召回购买不同的能力

BM25 按查询词匹配，并考虑词频和文档长度；Stanford 信息检索教材给出了这些因子的形式。DPR 的原始工作则通过双编码器学习问题和段落的稠密表示。两种表示可以成为对照基线，不能把某个开放问答数据集的结论直接搬到私有代码库。<sup><a href="#cite-3">[3]</a></sup><sup><a href="#cite-4">[4]</a></sup>

**工程取舍**：错误码、函数名和配置键需要保住精确标识符；自然语言同义表达可从语义召回中受益。中文分词、代码标识符拆分、embedding 模型和距离函数都影响结果。混合召回可以增加候选覆盖，但也增加重排与装配成本。

不能直接将两个检索器的原始分数相加：分数范围和标定通常不同。可以先用排序融合构造候选，再用统一重排器或规则排序。OpenAI 当前 Retrieval 文档提供语义与关键词混合检索的权重及排序阈值，说明这类策略有具体接口；这些字段属于该服务，不能当成所有向量库的标准配置。<sup><a href="#cite-5">[5]</a></sup>

## 用一个四候选例子定位错误

以下候选完全虚构。查询为“当前版本 `parse_invoice` 为什么退款为负”。

| ID | 候选 | 先检查什么 | 进入上下文的处理 |
|---|---|---|---|
| A | 当前 commit 的函数及调用处 | 标识符、版本、调用关系 | 保留必要行段与来源 |
| B | 两年前教程里的同名函数 | 是否仍适用于当前代码 | 作为历史材料标注，不能替代 A |
| C | 另一租户的金额配置 | 当前主体是否有读取权限 | 无权限则不返回内容 |
| D | 退款业务规则的当前说明 | 生效时间、规则与代码是否矛盾 | 与 A 配对，并保留冲突 |

如果 A 从未进候选，优先查查询和召回；A 已召回却被切得没有符号定义，查切分；A 和 D 都找到却只装入 B，查重排与预算；A、D 都在上下文里仍写错条件，才进入生成和工具行动归因。文档版本有冲突时，检索器不应凭相似度悄悄替用户作出业务决策。

重排器可以使用更丰富的 query–passage 交互，但增加计算和延迟。为了扩大召回而提高候选数，与为了减少噪声而提高阈值，是不同的旋钮。OpenAI 文档也明确较高阈值可能排除有用片段；应通过开发集选择，再在独立测试集报告结果。<sup><a href="#cite-5">[5]</a></sup>

## 上下文装配需要预算和证据关系

假设上下文输入上限为 16,000 个单位，为本轮输出预留 3,000，指令与工具占 3,000，保留的对话和任务状态占 4,000，则证据最多占 6,000。这里的数字只是算术示例；实际 token 计数、输出预留及隐藏开销必须按所用模型接口核对。

```text
可用证据预算 = 总窗口 − 输出预留 − 指令与工具 − 必保留状态
```

预算小于零时，应先报告无法装配，或调整允许调整的部分；不要静默截掉用户约束、待审批动作或未决工具结果。证据选择也不是只按分数截取前 k 条：A 的函数签名和 D 的规则可能需要成组保留；五个高度重复的 A 片段无法替代 D。

下面是**伪代码**，展示顺序与记录项，没有实现 tokenizer、权限系统或重排器：

```python
remaining = window - output_reserve - fixed_context_cost
if remaining < 0:
    raise ContextBudgetError()
selected = []
for group in rank_and_group(authorized_candidates):
    if group.is_current and group.token_cost <= remaining:
        selected.append(group.with_source_and_version())
        remaining -= group.token_cost
record_manifest(query, index_version, selected, remaining)
```

贪心装配容易遗漏低分但必要的证据，因此这段伪代码只能作为基线。更进一步需要任务依赖、证据多样性和缺失项检查；如果缺少必需规则，应继续读取或明确未知，不能因为“预算用满了”就开始生成确定答案。

Lost in the Middle 的原始 v1 摘要报告，所测模型与任务会受到相关信息位置和上下文长度影响。它提醒我们加入位置扰动测试，不证明 2026 年所有模型都有相同退化曲线，也不意味着把答案永远移到开头就能解决问题。<sup><a href="#cite-6">[6]</a></sup>

## 按需探索与预建索引如何组合

Anthropic 的工程文章讨论先保留路径等轻量引用，再通过工具按需读取；也讨论预先提供部分信息、运行中继续探索的混合方式。优点是减少一次性灌入，代价是额外探索回合和误入支路的可能。<sup><a href="#cite-1">[1]</a></sup>

对变化快的代码库，本文建议先用路径、符号、关键词定位当前工作树，再读取有关行段；对稳定的大文档集合，可以先用索引召回。两者都应记录观察版本。多轮检索只有在查询或新证据发生变化时才可能买到收益；同义改写十遍、反复读同一文件，可以更贵却没有更充分的证据。

摘要节省上下文，但摘要本身是新的派生产物。保留来源引用、关键约束、相互冲突的结论与未完成动作，允许后续回读原文；不要用摘要覆盖唯一的原始事件记录。长期经验写回与单轮证据选择仍需分开验收。

## 分阶段评测，才能知道该改哪里

先为固定任务集标注最小必要证据及最终交付标准。可有多个正确证据集合，避免把某个 chunk ID 当作唯一真相。按查询类型分层：精确符号、语义改写、跨文档关系、过期版本、权限变化和无答案任务。

| 阶段 | 可检查的记录 | 典型指标与限制 |
|---|---|---|
| 召回 | 查询、索引版本、候选列表 | Recall@k：必要证据进入前 k 的比例；定义按证据还是任务计 |
| 排序 | 重排前后次序、过滤理由 | 首个相关结果位置或 nDCG；不能替代最终任务成功 |
| 装配 | 实际送入模型的证据清单与 token | 必要证据覆盖、重复率、越权或过时片段数 |
| 生成 | 引用与对应原文、产物差异 | 引用支持度、无答案时的拒答、独立任务验收 |
| 全链路 | 总轮数、检索与模型费用、时延 | 每成功任务成本及尾部延迟；单列环境失败 |

Recall@k 在本文指“检索到的已标注必要证据数 / 已标注必要证据总数”；测试集没有任何必要证据的无答案题应单列，不能除以零或计作满分。引用看起来格式正确，也不说明原文支持了对应断言。

推荐做三组未执行的对照：无检索与基础检索；稀疏、稠密与混合；固定索引检索与受限的按需探索。固定模型、总预算、数据快照和 grader，同时单列调参集。再做删除关键证据、插入同名旧文件、重复片段与位置重排的扰动，观察系统是否保留未知，而非用无关内容补出答案。

## 学习练习与继续阅读

不用付费 API 也能先完成一个手工实验：写十个小文档，其中放入旧版本、近义词、精确错误码和无答案问题；手工标注证据，用关键词基线记录候选，再按固定字符预算装配。字符数只能作为练习刻度，不标成真实 token。检查每个失败发生在哪一段，再决定是否值得增加 embedding 或重排器。

随后到[执行循环实验室](../tools/loop-lab.html)观察证据不足时的核对动作怎样消耗预算，继续读[执行循环基础](agent-loop.html)与[记忆研究](agent-memory.html)。完整学习顺序及未覆盖主题见[学习地图](../learn.html)。
